# 移动构造与移动赋值：把"你的资源直接给我"

![移动语义：临时对象的堆资源直接接管、源指针置空、析构成空操作；普通拷贝 vs 移动构造对照](/assets/images/cpp-advanced/cpp-advanced-02-move-ctor-assign.png)

上一篇结尾留下 11 次函数调用的大账本，其中最冤的一笔是：**main 栈帧上的临时对象费劲拷贝了 tmp 的堆资源，语句一结束 tmp 和临时对象双双析构**——好比朋友花一千块买了东西，自己也照价买了一份，刚到手朋友说"早说我直接给你啊"。

这份冤枉账的解药是 C++11 的**移动语义**：给类增加两个新成员方法——**带右值引用参数的拷贝构造（移动构造）与带右值引用参数的赋值（移动赋值）**。它们不做拷贝，只做"资源接管"：把临时对象的堆指针直接拿来，源指针置空。

边界：右值引用的语法基础（左值/右值判定、`&&` 是右值引用不是二级引用）沿用第 07 篇；本篇以 CMyString 为例手工实现，标准库的 `std::move`/`std::forward` 是下一篇的主角。

## 1. 先把右值判定的三句话捋直

移动构造的参数是右值引用，"什么会被匹配进来"决定了它何时生效。三句判定话，全部有实验支撑：

**其一：有内存、有名字的是左值。**`int a` 是左值；字面量 `20` 没内存（在寄存器/指令里）没名字，是右值；函数返回的临时对象没名字，也是右值。

**其二：const 引用与右值引用都能绑右值，底层指令一模一样，区别只有一个。**`const int& d = 20;` 与 `int&& e = 20;` 反汇编逐条相同——都是产生临时量、取其地址、存入引用底层。唯一区别：`d` 被 const 锁死不能改临时量，`e` 没锁**可以改**。这个"可改"就是移动语义的入口：右值马上要死了，改它 = 合法地拆它的资源。

**其三：右值引用变量本身是左值。**`int&& e = 20;` 里的 `e` 有内存（4 字节引用底层）有名字，完全符合左值定义——再引用它得用左值引用。这句话是下一篇 `move`/`forward` 存在的全部理由，先埋好。

## 2. 移动构造：接管而不是拷贝

CMyString 的成员是一根指向堆字符串的指针。普通拷贝构造按源对象尺寸开新内存、拷数据——对临时对象这份拷贝纯属浪费。给类加上新版本：

```cpp
// 带右值引用参数的拷贝构造（移动构造）
CMyString(CMyString&& str) : mptr(str.mptr)
{
    str.mptr = nullptr;          // 关键一步：源指针置空！
    cout << "移动构造";
}
```

与普通拷贝构造的差异就两处：参数是 `CMyString&&`（只能被右值匹配——临时对象没名字没内存）；函数体**不开辟内存、不拷数据**，直接把源对象的指针抄过来，然后把**源指针置空**。

置空这步千万不能省，它防的是第 14 篇的双重析构：两个对象的指针若指向同一块堆内存，后析构的那个会二次 delete——浅拷贝事故的翻版。置空之后，临时对象析构时 `delete nullptr`，什么也不做；资源完好地归了新对象。一次移动 = 零次内存开辟、零次数据拷贝。

**匹配规则**：普通对象有名字，匹配左值引用版拷贝构造；临时对象是右值，匹配右值引用版（移动构造）。两个版本构成重载（`const T&` 与 `T&&` 参数类型不同），编译器按实参的左值性选择——用户不写任何额外代码，分发自动完成。

## 3. 移动赋值：先还旧账，再接管

赋值版本比构造多一步——`this` 已存在，手里可能有旧资源（第 14 篇 operator= 的第②步在移动版里依然是铁律）：

```cpp
// 带右值引用参数的赋值（移动赋值）
CMyString& operator=(CMyString&& str)
{
    if (this == &str)            // 右值不会自赋值，防御性保留
        return *this;
    delete[] mptr;               // ① 还自己的旧账
    mptr = str.mptr;             // ② 接管临时对象的资源
    str.mptr = nullptr;          // ③ 源指针置空
    return *this;
}
```

三步走的移动版：还旧账 → 接管 → 置空。与深拷贝版 operator= 的差别只在中段：不开新内存、不拷数据。

## 4. 全链验证：同一份代码，账本大瘦身

getString 案例（上一篇的 11 次调用）一行不改，只在类里新增移动构造与移动赋值，重跑：

```text
构造 s1 → 构造 s2 → 构造 tmp
→ 移动构造（tmp → main 栈帧临时对象）   ← 原来是深拷贝
→ 析构 tmp（空操作：指针已置空）        ← 原来要释放堆内存
→ 移动赋值（临时对象 → s2）             ← 原来是深拷贝
→ 析构临时对象（空操作）                ← 原来要释放堆内存
→ 析构 s2 → 析构 s1
```

资源（那块堆字符串）从 tmp 诞生起**原封不动**，被指针接力传递：tmp → 临时对象 → s2，全程零开辟、零释放、零拷贝。原来的两次深拷贝（各含 malloc + strcpy）消失，两次析构变成空操作。对象越大、字符串越长，省下的越可观——服务器项目里 JSON 串动辄几 MB，差距是数量级的。

## 5. 工程视角：STL 全员标配

STL 容器的常用方法基本都提供左值/右值两版：`push_back(const T&)` 与 `push_back(T&&)`，拷贝构造与赋值同样双版本。上一篇 vector 里 `push_back(string("bbb"))` 匹配到右值版、把临时串的资源直接搬进底层数组——正是这套机制的现成红利（第 20 篇手写 vector 只写了 const 版，升级成双版本是 03 篇的实操）。

两个使用守则顺手立下。**守则一：**自定义了析构/拷贝的类（第 14 篇判据）在 C++11 下应当同时提供移动版——否则临时对象仍走深拷贝路径，优化红利拿不到。**守则二：**移动构造/赋值里源指针置空是硬性动作，漏写即双重释放；这也是"移动后的对象处于有效但未定义状态"的含义——它可以析构（空操作）、可以重新赋值，但别假设它还有内容。

## 小结

- 移动语义的动机：临时对象"刚拷贝完就析构"，深拷贝纯浪费——资源应当直接移交
- 右值判定三句话：有内存有名字 = 左值；20/临时量 = 右值；**右值引用变量本身是左值**（03 篇的地基）
- const 引用与右值引用绑右值的指令相同，唯一区别是能否修改临时量——"可改"让接管合法
- 移动构造：指针接管 + **源指针置空**（防双重析构）；移动赋值：还旧账 → 接管 → 置空
- 重载分发自动完成：普通对象匹配 `const T&` 版，临时对象匹配 `T&&` 版——调用方代码零改动
- 同一份 getString 代码：两次深拷贝变两次指针接力，全程零拷贝；STL 容器全员双版本标配

接管机制成立的前提是"参数真的是右值"。但右值引用变量本身是左值——当资源在函数内部层层传递时，谁负责把它"变回"右值？下一篇：`std::move` 与 `std::forward`。
