# 编译与链接（上）：从 .cpp 到 .o

![从 .cpp 到可执行文件的四步流水线：预编译、编译、汇编、链接](/assets/images/cpp-core/cpp-core-02-compile-stages.png)

面试里被问"说说 C++ 程序的编译链接过程"，能答出"先编译成 .o，再链接成可执行文件"已经算及格。但再追问一句 `.o` 里到底装了什么、为什么它不能直接运行，多数人就开始含糊了。

含糊的代价不在面试，在排查问题。两种报错看起来都像"出错"，却分属完全不同的阶段：

```text
error: 'sum' was not declared in this scope      ← 编译阶段
undefined reference to `sum(int, int)'           ← 链接阶段
```

分不清这两条，排查方向就会跑偏：前者改代码，后者改构建配置。

这篇文章把编译这一段拆开：四步各做什么、`.o` 文件的结构长什么样、符号表里的 `UND` 是什么意思、为什么编译完的指令里地址全是 0。读完你应该能对着 `objdump` 和 `readelf` 的输出，说出任意一个 `.o` 文件里有什么。

例子在 64 位 Ubuntu 上演示，命令是 `g++`；Windows 下 `.o` 换成 `.obj`，段结构一致，MSVC 的对应工具是 `dumpbin`。

## 1. 待解剖的工程

例. 两个文件，一共二十来行。

```cpp
// main.cpp
#include <cstdio>
extern int gdata;              // 外部全局变量：只有声明
int sum(int, int);             // 外部函数：只有声明
int data = 20;                 // 本文件定义的全局变量

int main()
{
    int a = gdata;
    int b = data;
    int ret = sum(a, b);
    printf("ret = %d\n", ret);
    return 0;
}
```

```cpp
// sum.cpp
int gdata = 10;                // sum.cpp 里定义的全局变量

int sum(int a, int b)
{
    return a + b;
}
```

工程里只有两个源文件，却交叉引用了一个全局变量（`gdata`）和一个函数（`sum`）。这个交叉正是后面所有故事的来源。

## 2. 四步流水线

![四步流水线顺序点亮：每步留一件产物](/assets/images/cpp-core/cpp-core-02-compile-build.gif)

工程里每个 `.cpp` 都是**单独编译**的，`main.cpp` 和 `sum.cpp` 互不通信。单独编译走四步：

1. **预编译**：处理所有 `#` 开头的指令，展开头文件、替换宏、走条件编译
2. **编译**：词法分析、语法分析、语义分析、代码优化，产出汇编代码
3. **汇编**：把汇编翻译成机器指令，打包成 `.o`（Windows 下是 `.obj`）
4. **链接**：把多个 `.o` 和静态库合并成可执行文件

前 3 步合起来叫"编译过程"，第 4 步单独叫"链接过程"。一条 `g++ -c main.cpp` 就完成了前 3 步，产出 `main.o`。

这里有个容易记混的点：**编译只处理一个源文件，链接才看得到整个工程**。所以 `main.cpp` 里的 `gdata` 和 `sum`，编译时不可能知道它们在哪儿——它们甚至可能在另一个 `.o` 里，也可能根本不存在。

## 3. 预编译：所有 `#` 开头的命令，除了 `#pragma`

预编译阶段处理的是以 `#` 开头的指令：

```cpp
#define MAX 100               // 宏替换
#include <stdio.h>            // 头文件展开（递归复制）
#ifdef DEBUG                  // 条件编译
...
#endif
```

有一个例外：`#pragma` 要活到链接阶段。

```cpp
#pragma comment(lib, "xxx.lib")      // 让链接器去链某个库
```

这条指令干的事是"给链接器提供材料"，预编译阶段把它处理掉就没意义了。同类还有指定入口函数的写法：

```cpp
#pragma comment(linker, "/ENTRY:start")   // 让程序从 start 开始跑，而不是 main
```

程序默认以 `main` 为入口，这条指令能让链接器把入口地址改成别的函数。这类指令必须留到链接器手里。

一句话记住：**除 `#pragma` 之外，所有 `#` 开头的命令都在预编译阶段处理完。**

顺带说个后果：宏不是变量，没有类型、没有作用域，只是"把这几个字符换掉"。所以宏展开出来的代码行号会错乱，报错信息里出现你没写过的代码，八成是宏搅的。

## 4. 编译：三种分析加一步优化

预编译产物（`.i`）交给编译器，这一阶段做四件事：

- **词法分析**：把字符流切成 token（关键字、标识符、字面量、运算符）
- **语法分析**：按语法规则搭抽象语法树，检查结构是否合法
- **语义分析**：检查类型、声明、参数个数——`error: 'sum' was not declared` 就在这儿报
- **代码优化**：`-O0` 到 `-O3` 决定优化强度，然后生成目标平台的汇编

注意最后半句："目标平台的汇编"。同一份源码，在 x86 上生成 x86 汇编，在 ARM 上生成 ARM 汇编；汇编语法风格还有 AT&T（Unix 传统，`mov %eax, %ebx`）和 Intel（Intel/NASM 风格）两套。

所以第 2 步的产物是**平台相关**的。这也是为什么交叉编译要到这一层才分叉：源码和预处理产物可以通用，汇编开始就不通了。

## 5. 汇编：产出"可重定位"的目标文件

第 3 步把汇编翻译成机器码（01 串），产出的东西叫**二进制可重定位目标文件**（relocatable object file）。

这个名字里每个词都有用：

- **二进制**：已经是机器码了，不是文本
- **可重定位**：里面的地址还没定，可以被链接器挪位置、重填引用
- **目标文件**：不是最终程序，是"半成品"

所以 `.o` 不能运行。原因有两个，这篇讲第一个（地址没分配），下一篇讲第二个（符号没齐）。

## 6. 解剖 `.o`：先看文件头

`.o` 在 Linux 下是 ELF 格式（Windows 下是 PE 格式），`readelf -h` 看文件头：

```bash
g++ -c main.cpp -o main.o
readelf -h main.o
```

输出里有两行最值得看：

```text
Type:                              REL (Relocatable file)
Entry point address:               0x0
```

`Type` 是 `REL`，说明这是可重定位文件；`Entry point address` 是 0——一个能运行的程序不可能从 0 号地址开始执行（那是空指针区，访问即崩）。**光是这两行，就能判断一个文件能不能直接跑。**

## 7. 再看段：代码、数据、符号表

`readelf -S` 列出所有段：

```bash
readelf -S main.o
```

常见的几段：

| 段 | 放什么 | 标志 |
|---|---|---|
| `.text` | 机器指令 | `AX`（分配内存、可执行） |
| `.rodata` | 字符串字面量、常量 | `A`（只读） |
| `.data` | 已初始化的全局/静态变量 | `WA`（可写、占空间） |
| `.bss` | 未初始化（或为 0）的全局/静态变量 | `WA`，但不占文件体积 |
| `.symtab` | 符号表 | — |
| `.shstrtab` | 段名字符串表 | — |

`AX`、`WA` 这些标志直接对应下一篇要讲的虚拟地址空间：`.text` 会被映射成"可读可执行、不可写"，`.data` 会被映射成"可读可写"。

想看段里具体的内容，用 `objdump -s`：

```bash
objdump -s main.o
```

它会把 `.text` 里的机器码、`.data` 里的初值按十六进制打印出来。比如 `data = 20` 的初值，就能在 `.data` 段里看到 `14 00 00 00`（小端序）。

## 8. 符号表：`UND` 和 `G`/`L`

`.o` 里最关键的段是符号表，用 `objdump -t` 看：

```bash
objdump -t main.o | grep -E "data|main|gdata|sum"
```

`main.o` 的符号表大致是这样：

```text
0000000000000000 g     O .data    0000000000000004 data
0000000000000000 g     F .text    0000000000000045 main
                 *UND* 0000000000000000 gdata
                 *UND* 0000000000000000 _Z3sumii
```

逐列读：

- **值**：符号的偏移（此时还不是虚拟地址）
- **`g`**：global，其他文件也看得见
- **`O` / `F`**：对象（变量）还是函数
- **段**：`.data` 说明它定义在数据段，`.text` 说明定义在代码段
- **`*UND*`**：undefined，本文件只引用了它，没有定义

于是四种组合一眼可辨：

- `data`：本文件定义、已初始化、是全局符号 → 在 `.data`，`g`
- `main`：本文件定义的函数 → 在 `.text`，`g`
- `gdata`：只声明没定义 → `*UND*`
- `sum`：只声明没定义 → `*UND*`，而且名字被改成了 `_Z3sumii`

最后那个 `_Z3sumii` 就是 C++ 的名字改编（name mangling）。规则简单说就是"函数名 + 形参类型列表"编进符号名，因为 C++ 允许重载，光靠 `sum` 分不清是哪一个。

想知道 `_Z3sumii` 原本是哪个函数，用 `c++filt` 还原：

```bash
c++filt _Z3sumii
# sum(int, int)
```

反过来，`nm -C main.o` 或 `objdump -t -C main.o` 会直接把符号名显示成源码里的样子。

> 关键结论：**引用了外部符号，也会在自己文件里产生一条符号记录**，只不过这条记录是 `*UND*`。所以"只声明不定义"并不是"没有符号"，而是"有一个待解析的引用"。

那 `g` 和 `l` 的差别是什么？`l` 是 local，只在当前文件可见。你用 `static` 修饰全局变量或函数，生成的符号就变成 `l`，链接器根本看不见它。

这个特性很有用：多个 `.cpp` 里可以各写一个同名的 `static` 函数，互不冲突，因为它们都是 `l`。反过来，普通全局函数和全局变量是 `g`，整个工程里重名就会在链接时报冲突。

## 9. 为什么指令里的地址是 0

再看代码段的反汇编，加 `-r` 顺便把重定位记录一起打出来：

```bash
g++ -c main.cpp -o main.o -g
objdump -dr main.o | sed -n '/<main>:/,/^$/p'
```

会看到类似这样的内容：

```asm
  mov    0x0(%rip),%eax        # 读 gdata —— 地址填的是 0
  1b:  R_X86_64_PC32   gdata-0x4
  call   1b <main+0x1b>        # 调 sum —— 目标也填的是 0
  20:  R_X86_64_PLT32  _Z3sumii-0x4
```

两个 0 的含义是"这里要填一个地址，但现在还不知道填多少"。而 `R_X86_64_...` 那两行就是**重定位记录**：它记下"这条指令的哪个字节需要填哪个符号"，是编译器留给链接器的作业单。

原因就是第 2 节说的：编译 `main.cpp` 时，`gdata` 和 `sum` 都在别的文件里，编译器既不知道它们的段会被排在哪儿，也不知道它们存不存在。

那这些 0 谁来填？链接器。它拿到所有 `.o` 之后才有全局视角，才能算出每个符号的最终地址。这就是"编译期符号不分配虚拟地址，地址在链接期分配"的含义。

## 小结

- 每个 `.cpp` 独立编译，四步：预编译 → 编译 → 汇编 → 目标文件；多个 `.o` 再链接成可执行文件
- 预编译处理所有 `#` 开头的指令，唯独 `#pragma` 要留到链接阶段
- 编译做词法/语法/语义分析和优化，产品是平台相关的汇编
- 汇编产出 ELF 可重定位文件：`Type: REL`、`Entry point: 0x0`，因此不能直接运行
- `.o` 由段组成：`.text`（AX）、`.rodata`、`.data`（WA）、`.bss`、`.symtab` 等
- 符号表里，本文件定义的是 `g` 或 `l`，只引用的是 `*UND*`；`static` 会把符号降级成 `l`
- 引用外部符号的指令，地址先填 0——因为编译期还不分配虚拟地址
