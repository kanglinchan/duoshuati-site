# 编译与链接（下）：链接器把 0 填成了什么

![链接器把 .o 里的占位地址换成真地址：main.o → ld → a.out](/assets/images/cpp-core/cpp-core-03-linker.png)

上一篇留下的问题很具体：`main.o` 里读 `gdata` 的指令地址是 0，调 `sum` 的指令地址也是 0。两个 0 一天不改，程序一天跑不起来。

改它们的工具叫链接器（linker，命令 `ld`）。它比编译器多做了一件编译器做不到的事：**同时看见所有 `.o`**。

这篇文章讲链接的两个核心步骤、链接之后 `a.out` 比 `.o` 多了什么、以及程序真正跑起来时内存里发生了什么。读完你应该能解释：为什么 `.o` 里 `Type: REL`，而 `a.out` 就是可执行的；为什么入口地址写的是 `0x40018` 而不是 `main` 这个名字。

## 1. 链接的两个核心步骤

![链接过程：先合并段并解析符号，再分配地址与重定位](/assets/images/cpp-core/cpp-core-03-link.gif)

链接的输入是所有编译好的 `.o` 文件，加上静态库（Linux 的 `.a`，Windows 的 `.lib`）。输出是一个可执行文件（Linux 默认 `a.out`，Windows 是 `.exe`）。

中间干两件事：

1. **段的合并 + 符号解析**：把各文件的 `.text` 拼成一段、`.data` 拼成一段、`.bss` 拼成一段，符号表也合并；然后把所有 `*UND*` 的引用逐一找到定义
2. **符号重定位**：给每个符号分配虚拟地址，再回到代码段把那些 0 改成正确地址

第一步不通过就直接报错退出，第二步根本不会开始。所以"链接错误"其实分两族：符号找不到或重名，属于第一步；地址填错（极少见，通常是库版本问题）才属于第二步。

## 2. 第一步：段合并

上一篇说过，每个 `.o` 都是"按区域组织"的：`.text` 一段、`.data` 一段、`.bss` 一段、符号表一段。

合并的规则很直白——同类项相加：

```text
main.o 的 .text  +  sum.o 的 .text   →  a.out 的 .text
main.o 的 .data  +  sum.o 的 .data   →  a.out 的 .data
main.o 的 .bss   +  sum.o 的 .bss    →  a.out 的 .bss
```

段表、符号表也一样合并。

这里有个细节值得记住：**合并是从头到尾一次性完成的，不是"先合代码段、再合数据段"分几轮**。所以合并完的那一刻，每个符号就已经有了一个"在最终文件里的位置"（此时还是段内偏移），下一步才把它换算成虚拟地址。

## 3. 符号解析：必须给每个 `*UND*` 找到定义

合并完符号表，链接器手里有一堆符号。有的带着定义（在本文件的 `.text` 或 `.data` 里），有的标着 `*UND*`。

符号解析（symbol resolution）就是：**给每一个 `*UND*` 引用找到它的定义**。

`main.o` 里有两个 `*UND*`：`gdata` 和 `_Z3sumii`。链接器去 `sum.o` 的符号表里翻，找到了 `gdata`（定义在 `.data`）和 `_Z3sumii`（定义在 `.text`）。这一对引用就解决了。

两种失败情况，对应两个经典报错：

```text
undefined reference to `gdata'        # 翻遍了所有 .o 都没找到定义
multiple definition of `gdata'        # 找到了不止一处定义
```

第一条上一篇已经处理过：只声明、没定义，或者定义所在的 `.cpp` 没参与编译链接。

第二条的原因是"工程里全局名字不能重名"。但注意 `static`：`static` 全局变量和 `static` 函数的符号是 `l`（local），链接器根本看不见，所以多个文件里各写一份同名的 `static` 函数不会冲突。

这解释了 C++ 里一个常见写法：头文件里定义函数时用 `inline` 或 `static`，就是为了让每个包含它的 `.cpp` 各自拿到一份"本地"副本，避免链接时撞名。

## 4. 第二步：分配地址并重定位

符号解析全部通过后，链接器开始真正"排版"：给每个段、每个符号分配虚拟地址。

分配完，回到代码段干一件事——照着上一篇看到的 `R_X86_64_...` 作业单，把 0 改成真地址：

```text
改之前：call 1b <main+0x1b>        （目标 0）
改之后：call 4004d6 <sum>          （目标已确定）
```

这一步叫符号重定位（relocation）。"可重定位文件"这个名字就是从这里来的：它里面的地址是"等着被重定位"的。

改完的结果，就是我们上一篇说的"地址全都定死了"——每条跳转、每次全局变量访问，都是确定数字。

## 5. 手动走一遍：`ld -e main`

`g++` 只是司机，真正干活的是 `ld`。为了看清链接输入了什么，可以自己调：

```bash
ld -e main main.o sum.o -o a.out
```

`-e main` 指定入口函数。不指定的话，`ld` 默认找 `_start`（那是 C 运行时的启动代码），而我们这里没有链 `crt` 系列，所以要手动指明从 `main` 开始。

> **注意：** 如果 `main.cpp` 里还调了 `printf`，这条 `ld` 命令会报 `undefined reference to 'printf'`——因为 libc 没参与链接。这不是命令写错了，反而印证了符号解析的规则。演示时先把 `printf` 那行去掉，或者接受这个报错并观察它。

链接完，先看符号表：

```bash
objdump -t a.out | grep -E "gdata|sum|main"
```

和上一篇 `main.o` 的符号表对比，变化很直观：`*UND*` 没了，`gdata` 和 `sum` 后面都带上了地址。

再看代码段：

```bash
objdump -d a.out | sed -n '/<main>:/,/^$/p'
```

之前那两个 0，现在变成了具体的地址（比如 `0x404040`、`0x4004d6`）。

## 6. `a.out` 比 `.o` 多了什么

`readelf -S a.out` 会发现：段的种类几乎一模一样，`.text`、`.data`、`.bss`、`.symtab`、段表都在。

差别只有两处，但都是决定性的。

**第一处，文件头里的入口地址不再是 0。**

```bash
readelf -h a.out
```

`Entry point address` 变成了一个真实地址（64 位 Ubuntu 上典型是 `0x40018` 这个量级）。这个地址指向哪里？指向 `main` 的第一条指令。

```bash
objdump -d a.out | head -20
```

反汇编里第一条就是 `000000000040018 <main>` 之类的标签——和文件头里的入口地址对得上。

你自己跑的时候数值可能不同：用 `ld -e main` 手动链接时 `main` 离 `0x400000` 很近（`0x400078` 这个量级），用 `g++` 链接了 crt 启动代码后通常落在 `0x4004xx`~`0x4005xx`，入口则变成 `_start`。对齐关系一样，别死记数字。

这就是"程序从哪开始执行"的答案：CPU 不认 `main` 这个名字，它只认文件头里那个数字。把入口地址改成 `sum` 的第一条指令，程序启动就会先跑 `sum`——这也是 `#pragma` 那类指令能改入口的原理。

**第二处，多了一张"程序头表"（program headers）。**

```bash
readelf -l a.out
```

输出里有两个 `LOAD` 段：

```text
LOAD  ...  R E      ← 代码段：可读、可执行
LOAD  ...  RW       ← 数据段：可读、可写
```

这两个 `LOAD` 是给操作系统看的：**运行这个程序时，把这两块内容从磁盘搬进内存**。

注意"只搬两块"这件事。`.symtab`、`.shstrtab` 这些段运行时有意义吗？没有——符号表只给调试和链接用，程序跑起来不需要它。所以程序头表里只列了真正要加载的东西。

## 7. 运行时：从磁盘到虚拟地址空间

链接完成的 `a.out` 躺在磁盘上。双击（或 `./a.out`）之后，发生的事大致是：

1. 操作系统读 ELF 头，拿到入口地址
2. 读程序头表，把两个 `LOAD` 段映射到当前进程的虚拟地址空间（代码段映射到代码区、数据段映射到数据区）
3. 把入口地址写进 CPU 的 PC 寄存器
4. CPU 从 `main` 的第一条指令开始执行

第 2 步要特别强调：映射的不是物理内存，是**虚拟地址**。

也就是说，程序刚起来时，代码段和数据段在物理内存里可能还没有真正的页——只有虚拟地址到"某处"的映射约定。等 CPU 真的访问某个还没落到物理页的地址时，会触发一次缺页异常（page fault），异常处理程序才去分配物理页，填好页表，然后让那条指令重新执行。

这就是为什么"程序占用了 1G 内存"和"程序实际用了 1G 物理内存"是两回事——虚拟地址空间的数字只是账面，物理内存是按需给的。

## 小结

- 链接输入是所有 `.o` 加静态库，输出可执行文件；中间两步：合并段与符号解析、分配地址与重定位
- 符号解析的任务是给每个 `*UND*` 找到定义；找不到报 `undefined reference`，找到多处报 `multiple definition`
- `static` 符号是 local（`l`），链接器看不见，所以多个文件里可以各有同名 `static`
- 重定位 = 照着重定位记录，把指令里的 0 改成真地址
- `a.out` 与 `.o` 的段几乎相同，差别是：入口地址不再是 0，且多了程序头表
- 程序头表里只有两个 `LOAD`（代码段 `R E`、数据段 `RW`），符号表这类段不加载
- 加载是把段映射进虚拟地址空间，物理内存按需分配，缺页时由异常处理程序补上

内功篇到这里还剩最后一讲：把程序眼里的那张内存地图完整画出来——全局变量、局部变量、`malloc` 出来的东西，各自落在 4G 地址空间的哪一段。
