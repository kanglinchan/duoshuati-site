# 抽象类：把"只能被继承"写进语法

![抽象类：纯虚函数 = 0，不能实例化对象但可以指针/引用；行车电脑案例的通用公式与变化点分离](/assets/images/cpp-core/cpp-core-31-abstract-class.png)

上一篇的 Animal 类里，`bark()` 的函数体是空的。写空函数体是在撒谎——它暗示"动物会叫，只是这里先不实现"，可真相是：**"动物怎么叫"这个问题问 Animal 本身就没有答案**。动物是个泛指，猫叫、狗叫才有意义。

既然基类方法的实现本来就不该存在，C++ 给了个干脆的语法：函数体都不用写，直接 `= 0`。这就是**纯虚函数**，而拥有纯虚函数的类成为**抽象类**——编译器强制它"只能被继承、不能被实例化"。

这篇讲清纯虚函数与抽象类的规则，再用一个"行车电脑"的实战案例展示抽象类的真正用法：把通用公式放进基类，把变化点声明为纯虚留给派生类。

边界：纯虚析构函数的特殊规则在笔试题篇；"接口类"（全是纯虚函数的抽象类）与设计模式属于进阶内容。

## 1. 基类的初衷决定了它的形态

定义 Animal 的初衷是什么？回头看它提供的两样东西：`name` 属性给所有动物复用（继承意义①：代码复用），`bark()` 给所有动物保留统一的覆盖接口（继承意义②：多态解耦）。

**Animal 从来就不是为了描述"一只具体的动物"而存在的。**Cat、Dog 各自抽象一个实体类型，Animal 只是它们的公共部分 + 统一接口的载体。既然如此，`bark()` 在 Animal 里就没有合理实现——不是"暂时没写"，是**逻辑上写不出来**。

C++ 的表达方式：

```cpp
class Animal
{
protected:
    string name;
public:
    virtual void bark() = 0;     // 纯虚函数：只有声明，没有实现
};
```

`= 0` 表示"此函数只有接口、没有函数体"。一个函数写作纯虚，传递的设计意图是：**我知道派生类需要这个能力，但它怎么实现由派生类全权决定，基类无权也无能代言。**

## 2. 纯虚函数与抽象类：语法规则

**拥有纯虚函数的类是抽象类**（abstract class），规则两条，正反各一条：

- **不能实例化对象。**`Animal a;` 编译错误——一个连行为都定义不全的类型，没资格直接造对象。这条规则是编译器替你把关的设计约束：谁想在业务代码里 new 一个 Animal，编译器直接拦下。
- **可以定义指针和引用。**`Animal* p; Animal& r = cat;` 完全合法——而多态恰好只需要这两样（第 30 篇：基类指针指向派生对象，调用同名覆盖方法）。

这两条规则拼起来严丝合缝：抽象类**禁止**了你唯一用不到的用法（实例化对象），**保留**了你唯一需要的用法（指针/引用 + 多态）。语法与设计意图完全对齐——这就是抽象类存在的意义：**用编译器强制执行"这个类只能作为接口基类使用"**。

抽象类与普通类的区别也因此分两层回答。语法层：普通类实例化对象、指针、引用三样都行，抽象类只剩指针和引用。语义层：**普通类抽象某个实体类型**（Cat 抽象猫），**抽象类不抽象实体，只为派生类提供复用的成员与统一的接口**。顺带一个派生侧规则：派生类重写纯虚函数之前自己也是抽象类（没把所有纯虚函数都实现的派生类，同样不能实例化）——保证接口最终落在能实例化的具体类上。

## 3. 实战：行车电脑，通用公式与变化点分离

抽象类的典型应用长什么样？看一个例子：给汽车行车电脑写模块——显示当前油量下还能跑多远。

先想清楚哪些是通用的、哪些是变化的。**通用公式**：剩余里程 = 每加仑油能跑的公里数 × 剩余油量。这个公式对任何车都成立，可以放进基类。**变化点**：每加仑能跑多少公里——奔驰、奥迪、宝马各不相同，基类写不出来。

```cpp
class Car
{
protected:
    string name;
    double oil;                              // 剩余油量
    virtual double getMilesPerGallon() = 0;  // 变化点：纯虚，protected（只给派生类用）
public:
    Car(string n, double o) : name(n), oil(o) {}
    string getName() const { return name; }
    double getLeftMiles()                    // 通用公式：基类就能写
    {
        return getMilesPerGallon() * oil;    // 调虚函数 → 动态绑定
    }
};

class Benz : public Car
{
public:
    Benz(string n, double o) : Car(n, o) {}
    double getMilesPerGallon() { return 20.0; }   // 奔驰：一加仑 20 公里
};
class Audi : public Car
{
public:
    Audi(string n, double o) : Car(n, o) {}
    double getMilesPerGallon() { return 18.0; }   // 奥迪：18 公里
};
```

看 `getLeftMiles()` 这行——它是整个设计的点睛之处：**基类的普通方法调用基类的纯虚函数**。公式部分基类写死，变化部分留给虚函数；调用时动态绑定生效（基类引用/指针调用虚函数），`benz.getLeftMiles()` 走 Benz 的表拿到 20，`audi.getLeftMiles()` 拿到 18。同样一箱油，行车电脑显示的里程不同——查表查出来的。

统一的对外 API 也水到渠成：

```cpp
void showCarLeftMiles(Car& car)
{
    cout << car.getName() << " 还能跑 "
         << car.getLeftMiles() << " 公里" << endl;
}
```

新增宝马？继承 Car、重写 `getMilesPerGallon` 返回 19，接口零改动——开闭原则（第 30 篇）再次生效。

这个结构值得多看一眼：**基类实现通用骨架，纯虚函数挖出变化点，派生类只填变化**。变化点 `getMilesPerGallon` 声明为 protected——它是派生类的"填空题"，外部没有理由直接问"你一加仑跑几公里"（第 26 篇：给派生类访问、对外封死）。这个模式在软件设计里有个名字（模板方法），设计模式篇再展开，这里先把代码层面吃透。

## 4. 面试标准答案

"什么类设计成抽象类？为什么？"按这个层次答：

1. **基类**一般设计成抽象类——基类的初衷不是抽象某个实体，而是给派生类提供代码复用与统一覆盖接口；
2. 基类中**给派生类保留的统一接口**，实现成纯虚函数（基类往往也不知道该怎么实现）；
3. **好处**：抽象类不能实例化，从语法上强制"它只能被继承使用"，防止误用；接口统一后多态可用，接口与派生类解耦，符合开闭原则；
4. **与普通类的区别**：语法上抽象类不能实例化对象（可以指针/引用），普通类都可以；语义上抽象类不描述实体、只承载公共部分与接口。

## 小结

- 纯虚函数 `virtual f() = 0`：只有接口没有实现——"基类无权代言这个行为"
- 抽象类 = 拥有纯虚函数的类：不能实例化对象，可以定义指针和引用——恰好删掉用不到的、保留唯一需要的
- 抽象类不抽象实体，只为派生类提供公共成员与统一接口；派生类没实现全部纯虚函数前自己也是抽象类
- 实战范式：通用公式放基类普通方法，变化点声明为 protected 纯虚函数，派生类填空——基类方法调纯虚函数，动态绑定生效
- 新增派生类 = 继承 + 重写，接口零改动（开闭原则）；新增一个纯虚函数等于给所有派生类派作业
- 面试答案四层：基类设计成抽象类 / 统一接口用纯虚 / 强制继承+解耦 / 语法语义两层的区别
