# 不带引用计数的智能指针：一个资源，到底归谁管

![auto_ptr 转移所有权之坑 / scoped_ptr delete 删函数 / unique_ptr 显式 move——三种流派](/assets/images/cpp-advanced/cpp-advanced-06-unique-ptr.png)

上一篇的极简智能指针有个致命伤：`p2(p1)` 浅拷贝后双重释放崩溃。治法有两条路线——**不让两个指针管同一资源**（本篇），或者**数着人数管**（引用计数，07 篇）。

"不让管"这一派内部又有三种流派，对应三个标准库成员：auto_ptr 偷偷转移所有权（已被 C++17 移除）、scoped_ptr 直接删除拷贝（C++98 boost 系）、unique_ptr 删除拷贝 + 放行显式 move（C++11 推荐本派之王）。三者的差异浓缩成一道面试题：**拷贝发生时，你希望用户感知到什么？**

边界：本篇带 memory 头文件的三兄弟；weak_ptr 与 shared_ptr 是下一篇；unique_ptr 与删除器的配合在 08 篇补齐。

## 1. 先诊断：浅拷贝与"反直觉的深拷贝"

auto_ptr 的拷贝构造走默认浅拷贝 → 双重析构崩溃（老朋友）。那按第 14 篇的套路自定义深拷贝呢？也救不了——**智能指针的场景里深拷贝是错的**：

- 用户写 `p2(p1)` 的意图很明确：**让两个指针管同一块资源**（指针的本义）；
- 深拷贝版却给 p2 开了一块新内存——p1、p2 从此管着两块互不相干的资源，`*p1 = 30` 后 `*p2` 纹丝不动；
- 用户视角：我要的是"共享"，你给我的却是"复制"——语义全歪。

所以智能指针的拷贝问题不能套普通对象的深拷贝药方。三条流派，本质是三种"回答用户意图"的方式。

## 2. auto_ptr：偷偷转移所有权（反面教材）

auto_ptr 的策略是**转移**——拷贝构造时把源指针的资源直接接管，源指针置空：

```cpp
auto_ptr<int> p1(new int(10));
auto_ptr<int> p2(p1);        // p2 接管资源，p1 底层指针置空
*p2 = 20;                    // 正常
*p1 = 30;                    // 崩溃！p1 已经是空指针
```

源码里能看清动作：拷贝构造调用 `release()`——把源指针记下、源指针置空、返回原地址给新对象。资源所有权从 p1 **悄悄地**转给了 p2。

问题就出在"悄悄"。用户对这场转移**毫无感知**：写拷贝构造的人多半以为只是共享，继续用 p1 就是空指针解引用。更恶劣的是容器场景——容器拷贝/赋值会逐元素拷贝构造，容器里的 auto_ptr 被成批转移置空，拷贝出来的容器元素全是空壳。基本 C++ 规范因此不推荐 auto_ptr，C++17 干脆把它移除。**教训：改变用户语义的行为绝不该静默发生。**

## 3. scoped_ptr：删除拷贝，一禁了之

boost 系的 scoped_ptr 策略最简单粗暴——**把拷贝构造和赋值直接删除**（`= delete`，第 16 篇的语法）：

```cpp
scoped_ptr<int> p1(new int(10));
scoped_ptr<int> p2(p1);      // 编译错误：引用已删除的函数
```

用户感知拉满——想拷贝？编译期直接拦下。代价也拉满：**任何形式的拷贝都不可用**，不能当函数参数传、不能当返回值、不能进容器（这些场景都需要拷贝）。scoped_ptr 的适用面缩到"单一作用域内独占管理"，使用率一直不高。

## 4. unique_ptr：删除拷贝 + 放行显式 move

C++11 的 unique_ptr 表面上与 scoped_ptr 同款——拷贝构造和赋值同样 delete。但区别在它**额外提供了带右值引用参数的拷贝构造与赋值**（第 02 篇的移动语义！）：

```cpp
unique_ptr<int> p1(new int(10));
unique_ptr<int> p2(p1);                    // ✗ 编译错误
unique_ptr<int> p2(std::move(p1));         // ✓ 显式 move：资源移交，p1 置空
```

`std::move` 把 p1 强转成右值（第 03 篇），匹配到 unique_ptr 的移动构造——资源移交、源指针置空。这就是 unique_ptr 名字的完整含义：**资源始终只有一个管理者**，唯一的"交接"通道是显式 move。

三流派的差别在用户感知，一次排开：

| | 拷贝时用户感知 | 后果 | 评价 |
|---|---|---|---|
| auto_ptr | 零感知，静默转移 | 源对象悄悄变空，后续使用崩溃 | 反面教材，已移除 |
| scoped_ptr | 编译期报错 | 想交接也无门 | 过度保守 |
| unique_ptr | **move 的显式动作** | 用户亲手写 move = 亲口承认"p1 不再持有" | 意图外显，推荐 |

move 的妙处正是**把意图写进代码**：写 `std::move(p1)` 的那一刻，用户已经知道"p1 让出去了"——交接从意外变成契约。函数传参/返回也因此打通：函数内部 `return unique_ptr<int>(new int);` 直接走移动构造（临时对象右值），unique_ptr 可以正常进出函数，而 scoped_ptr 做不到。

## 5. 选型口径

这一派的共识先说清：**不共享时才选它**。需要多个指针管同一资源，本派全部无能为力——那是 shared_ptr 的主场（07 篇）。

在本派内部：auto_ptr 直接从选项里划掉（已移除）；scoped_ptr 被 unique_ptr 完全覆盖（delete 拷贝它也做了，还多了 move 通道）；**结论只有一句——独占资源管理，用 unique_ptr**。它零引用计数开销（没有任何计数内存），资源释放时机确定（栈对象析构即释放，不数人数），是"默认就该用"的智能指针。

## 小结

- 智能指针的拷贝问题不能套深拷贝药方：用户意图是"共享资源"，深拷贝给出"两份资源"——语义全歪
- auto_ptr：release() 静默转移所有权，用户零感知继续用空指针——已从标准移除的反面教材
- scoped_ptr：`= delete` 删除拷贝构造与赋值，编译期一禁了之——过度保守，不能传参/返回/进容器
- unique_ptr：删除拷贝 + 提供移动版——显式 `std::move` 是唯一交接通道，意图外显成契约；可正常进出函数
- 三流派一句话：auto_ptr 偷偷给、scoped_ptr 死活不给、unique_ptr 你开口才给——用户感知逐级升格
- 选型：独占 → unique_ptr（零计数开销、释放时机确定）；共享 → 下一篇 shared_ptr
