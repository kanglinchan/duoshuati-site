# 工厂三兄弟：简单工厂、工厂方法、抽象工厂的演进线

![工厂演进：简单工厂（switch 增产品改老代码）→ 工厂方法（一产品一工厂）→ 抽象工厂（产品族）](/assets/images/cpp-advanced/cpp-advanced-17-factory-patterns.png)

工厂模式有三个成员——简单工厂、工厂方法、抽象工厂。既然功能相近，为什么要三种？**因为它们之间有区别**：三个模式是一条演进线上的三站，每一站解决上一站暴露的一个问题。

这篇按"演进"讲：从最朴素的简单工厂出发，看它违背开闭原则的地方，逼出工厂方法；再看"单一产品"的局限，逼出抽象工厂。读完三者的适用边界自然清晰。

边界：代码以"生产手机"为贯穿例子；与第 30 篇多态（虚函数 + 基类指针）的关系是本篇的实现底座。

## 1. 简单工厂：一个 switch 管所有产品

需求：客户端想要手机对象，但不想自己 new（new 什么型号、怎么配参数是客户端不该操心的细节）。简单工厂用一个静态方法按参数造对象：

```cpp
class SimpleFactory
{
public:
    static Phone* create(const string& brand)
    {
        if (brand == "HuaWei")  return new HuaWeiPhone();
        if (brand == "XiaoMi")  return new XiaoMiPhone();
        return nullptr;
    }
};

Phone* p = SimpleFactory::create("HuaWei");    // 客户端只认抽象 Phone
```

好处立竿见影：客户端面向抽象 `Phone` 编程（第 30 篇多态），不接触具体型号的构造细节。

但它有一个致命伤：**新增品牌要改 create 的 if-else——修改老代码**。开闭原则（第 30 篇：对修改关闭、对扩展开放）在简单工厂这里直接破产——加一个 Vivo，就得打开 SimpleFactory 改它。产品类型越多，这个 switch 越臃肿，而且"新增产品"和"工厂代码"这两个本不相干的变更被焊死在一起。

## 2. 工厂方法：一个产品配一个工厂

工厂方法的解法是把"新增"变成"扩展"：**给每个产品配一个专属工厂，工厂们实现同一个抽象工厂接口**——新增品牌 = 新增一对类（产品 + 工厂），老代码一行不动：

```cpp
class PhoneFactory                       // 抽象工厂接口
{
public:
    virtual Phone* create() = 0;
    virtual ~PhoneFactory() {}
};

class HuaWeiFactory : public PhoneFactory
{
public:
    Phone* create() { return new HuaWeiPhone(); }
};
class XiaomiFactory : public PhoneFactory
{
public:
    Phone* create() { return new XiaomiPhone(); }
};

PhoneFactory* pf = new HuaWeiFactory();  // 客户端面向抽象工厂
Phone* p = pf->create();
```

新增 Vivo：写 `VivoPhone` + `VivoFactory` 两个新类——**对修改关闭（谁也没改）、对扩展开放（新增一对类）**，开闭原则达标。这就是工厂方法与简单工厂的本质区别：**简单工厂把"产品的选择"放在一个函数的分支里（改老代码），工厂方法把"产品的选择"交给多态（新增新类）**。

代价也要看清：类的数量翻倍（每个产品多一个工厂），产品一多工程里工厂类泛滥——简单工厂在"产品少且稳定"的场景反而更轻。选型不是越"高级"越好，是看变更模式：**产品会持续新增 → 工厂方法；产品稳定 → 简单工厂够了**。

## 3. 抽象工厂：从"单个产品"到"产品族"

工厂方法管住了"单一产品的新增"，但现实里产品常常**成族出现**：华为不只生产手机，还有华为的耳机、华为的转接头——同一品牌的产品族有关联关系，客户要的是"华为全家桶"，而不是"一台华为手机 + 随便什么耳机"。

工厂方法在这个场景的尴尬：手机工厂、耳机工厂各自独立，客户端组装时可能配出"华为手机 + 小米耳机"的混搭。抽象工厂的解法：**一个工厂管一族产品**——抽象接口里放该族所有产品的 create 方法：

```cpp
class PhoneFactory          // 抽象工厂：一族产品的完整生产线
{
public:
    virtual Phone* createPhone() = 0;
    virtual Headset* createHeadset() = 0;      // 同族产品都出自这一家
    virtual ~PhoneFactory() {}
};

class HuaWeiFactory : public PhoneFactory
{
public:
    Phone* createPhone()   { return new HuaWeiPhone(); }
    Headset* createHeadset() { return new HuaWeiHeadset(); }   // 保证配 Huawei 耳机
};
```

客户端拿到的"华为工厂"生产出来的所有产品天然同族——**产品族的配对约束由工厂类型本身保证**，客户端想配错都难。新增品牌 = 新增一个族工厂（实现全部 create）；新增产品族里的新产品（比如新增平板）= 修改抽象接口 + 所有工厂——这一步**又要改老代码**，是抽象工厂的固有代价：**它擅长"增族"，不擅长"增产品种类"**（后者是工厂方法的主场）。

## 4. 三站对比表

| | 简单工厂 | 工厂方法 | 抽象工厂 |
|---|---|---|---|
| 形态 | 一个静态方法 + 分支 | 一产品一工厂，实现统一接口 | 一工厂一族产品 |
| 新增产品 | 改工厂（违反开闭） | 新增一对类（开闭达标） | 新增一个族工厂 |
| 新增产品种类 | 改工厂 | 新增一对类 | **改抽象接口 + 全部工厂**（弱点） |
| 强项 | 产品少且稳定 | 单产品持续扩展 | 产品族的整体替换与配对 |
| 弱点 | 违背开闭 | 类数量翻倍 | 增"种类"要动老代码 |

一句话收束：**简单工厂管"造"，工厂方法管"扩展着造"，抽象工厂管"一族一起造"**——三者不是替代关系，是变更模式不同时的三个落点。

## 小结

- 简单工厂：静态方法 + if-else——客户端解耦构造细节，但新增产品改老代码，开闭破产
- 工厂方法：一产品一工厂实现统一接口——新增变扩展（新增一对类），代价类数量翻倍；产品稳定时简单工厂反而更轻
- 抽象工厂：一个工厂管一族产品——同族配对约束由工厂类型保证（华为工厂只产华为全家桶）；擅长增族、不擅长增种类
- 演进逻辑：每站解决上一站暴露的问题——分支改老代码 → 多态扩展 → 族内配对
- 底座全是第 30 篇多态：客户端面向抽象产品 + 抽象工厂编程
- 选型看变更模式：持续加品牌 → 工厂方法；族要整体替换 → 抽象工厂；产品稳定 → 简单工厂

创建型模式收官。下一篇结构型与行为型：代理/装饰器/适配器管"功能怎么用"，观察者管"对象怎么通信"。
