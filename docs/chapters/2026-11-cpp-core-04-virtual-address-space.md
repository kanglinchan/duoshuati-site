# 进程虚拟地址空间：程序看到的内存地图

![32 位 Linux 进程的 4G 虚拟地址空间：内核空间、栈、共享库、堆、.bss、.data、.rodata、.text、保留区](/assets/images/cpp-core/cpp-core-04-vas.png)

面试里有一道很常见的题：你说说，代码里的全局变量、局部变量、`malloc` 出来的内存，运行的时候都放在哪儿？

很多人答"静态区""全局变量区"。这个答案不能算错，但不准确——在正规的教材和手册里，没有这几个名词。专业说法是代码段、数据段、BSS 段、堆、栈。

这篇文章把 32 位 Linux 进程的 4G 地址空间从上到下走一遍：每一段放什么、为什么这么排、以及一个很容易搞混的问题——**局部变量在符号表里为什么找不到**。

边界：全程以 **32 位 Linux**（`x86`）为准，用户空间 3G、内核空间 1G。64 位的划分比例和段的起始地址都不同，本文不涉及；内核空间的三个 zone 只在最后提一句。

## 1. 4G 空间是内核造出来的假象

程序运行时，内核会给这个进程"分配"一块 2³² 字节（4G）的区域。这块区域叫**进程的虚拟地址空间**（virtual address space）。

名字里"虚拟"两个字要当真。它不是物理内存上的 4G，甚至可以说它根本不存在——它只是内核维护的一系列数据结构（页表、VMA 链表之类）。

IBM 有个经典的四句话解释虚拟：

> 它存在，你能看得见，它是物理的；
> 它存在，你看不见，它是透明的；
> 它不存在，你却看得见，它是虚拟的；
> 它不存在，你也看不见，它被删除了。

虚拟地址空间属于第三种：不存在，但程序看得见。

顺便区分两个词：**虚拟内存**和**虚拟地址空间**不是一回事。前者是内存管理机制，后者是进程眼里的地址范围。混着用容易在面试里被追问到答不上来。

## 2. 一刀切开：用户 3G，内核 1G

![从低地址往上逐段点亮：保留区、代码段、数据段、堆、共享库、栈、内核空间](/assets/images/cpp-core/cpp-core-04-grow.gif)

4G 被切成两半：

- `0x00000000` ~ `0xBFFFFFFF`（3G）：**用户空间**（user space）
- `0xC0000000` ~ `0xFFFFFFFF`（1G）：**内核空间**（kernel space）

这个 3:1 是默认值，可以通过内核配置调整，但默认就是它。

两者最重要的差别不在大小，在归属：

- 用户空间是**每个进程私有**的，QQ 的栈和酷狗音乐的栈互不相干
- 内核空间是**所有进程共享**的，同一份内核代码、同一批内核数据结构

共享这件事有个直接的应用：匿名管道。两个进程的用户空间互相看不见，但它们都能访问内核空间里同一块缓冲区——一个往里写，另一个就能读到。进程间通信之所以要"经过内核"，就是因为用户空间被隔离了。

## 3. 用户空间：从低地址往上走

从 0 开始，用户空间的分段是这样的。

**保留区（0 ~ 0x08048000，128MB）**

这块地不给任何东西用，不可读也不可写。

为什么留？为了让空指针立刻崩。空指针的值是 0，`strcpy(dest, NULL)` 这种调用会从 0 号地址开始读，正好撞进不可访问区，程序当场挂掉。

如果 0 号地址可读，这类 bug 会变得非常隐蔽：读到一堆垃圾，程序继续往下跑，最后在几百行以外的地方出错。

**代码段 `.text`**

从 `0x08048000` 开始，存机器指令。

记住这个数字，也记住回答的措辞：指令放在**代码段**（或 `.text` 段），不要说"全局变量区"。

**只读数据段 `.rodata`**

字符串字面量、常量。`"hello world"` 就住在这里。

```cpp
const char* p = "hello";
p[0] = 'H';          // 编译能过，运行崩
```

`.rodata` 和 `.text` 都只读，写它们会触发保护异常。现在较新的 C++ 编译器干脆不让 `char*` 直接指向字面量，必须写成 `const char*`——从类型上就把这类错误挡住了。

**数据段 `.data`**

初始化了、而且初值不为 0 的全局变量和静态变量。

**BSS 段 `.bss`**

未初始化的、或初始化为 0 的全局变量和静态变量。

`.data` 和 `.bss` 都叫"数据段"，差别只在初值。为什么要分两个？因为 `.bss` 不占文件体积——它只需要在文件头里记一句"这块区域要多大、初值全是 0"，加载时由内核清零。

这解释了一个常见现象：

```cpp
int g;          // 全局，未初始化
int main() { printf("%d\n", g); }    // 打印 0
```

`g` 没初始化，打印出来却是 0。不是编译器偷偷帮你赋了 0，是因为它住在 `.bss`，**内核在进程启动时把整段清零**。同理，`static` 局部变量虽然没初始化，打印也是 0。

**堆**

`.bss` 之上是堆，程序调 `new` 或 `malloc` 时才在这里分配，**从低地址向高地址生长**。

**共享库映射区**

`printf`、`malloc` 这些函数的代码不在你的可执行文件里，它们在动态链接库里（Linux 的 `.so`，Windows 的 `.dll`），运行时被映射到这一段。

**栈**

从用户空间的顶部往下，**从高地址向低地址生长**。局部变量、函数参数、返回地址都在这儿。

再往上一小块，是命令行参数和环境变量——`main` 的 `argv`、`envp` 指向这里。所以你运行 `./a.out 192.168.1.100 9090`，这两个参数就在栈的最顶端附近。

还有一个容易忽略的点：**栈是每个线程一份**。进程里开三个线程，就有三个独立的栈；而代码段、数据段、堆是这个进程所有线程共享的。

## 4. 局部变量为什么不产生符号

这是本节最值得记住的一条。

上一篇讲到编译时会生成符号表。那么问题来了：`main` 里定义的局部变量 `a`，会不会在符号表里产生一个叫 `a` 的符号？

不会。

局部变量不产生符号。编译器为它生成的是一条指令：

```asm
mov dword ptr [ebp-4], 0Ch     ; 把 12 写进 a 的内存
```

这条指令本身属于代码段（`.text`）。真正"分配 4 个字节给 `a`"这件事，发生在函数运行的时候——函数进来先 `sub esp, n` 开栈帧，那 4 个字节才存在。

所以"局部变量在栈上"和"局部变量的定义产生了指令"这两句话不矛盾：

- 编译期：产生一条写内存的指令，指令进 `.text`
- 运行期：这条指令执行时，往栈帧里的某块空间写值

搞混这一点，就很容易在面试里说错"局部变量存在代码段"或者"局部变量有符号"。

## 5. 六种变量，各归其位

把上面所有规则套到一个具体例子上。

```cpp
int g1 = 10;              // .data
int g2 = 0;               // .bss
int g3;                   // .bss

static int s1 = 10;       // .data
static int s2 = 0;        // .bss
static int s3;            // .bss

int main()
{
    int a = 10;           // 栈（编译期只产生指令）
    int b = 0;            // 栈
    int c;                // 栈

    static int t1 = 10;   // .data
    static int t2 = 0;    // .bss
    static int t3;        // .bss
    return 0;
}
```

规律很整齐：

| 变量 | 段 | 理由 |
|---|---|---|
| `g1`、`s1` | `.data` | 有初值且不为 0 |
| `g2`、`g3`、`s2`、`s3` | `.bss` | 初值为 0 或没有初值 |
| `a`、`b`、`c` | 栈 | 不产生符号，只产生指令 |
| `t1` | `.data` | 静态局部变量也在数据段 |
| `t2`、`t3` | `.bss` | 同上，初值为 0 或未初始化 |

`static` 局部变量还有一个特别之处：它在数据段，但**程序启动时不初始化**，第一次执行到它所在的语句时才初始化。所以它能在多次调用之间保持值——这一点和普通局部变量完全不同。

## 6. 内核空间那 1G

用户空间讲完，简单补一下 1G 的内核空间。它分成三个 zone：

- **ZONE_DMA**：大约 16MB，给早期只能访问低 24 位地址的设备用
- **ZONE_NORMAL**：大约 800 多 MB，内核的主要工作区——进程控制块（PCB）、内核栈、内核代码都在这里
- **ZONE_HIGHMEM**：高端内存，做物理内存映射用

以"第一部分只讲到用户空间"为标准的话，这三个 zone 记住名字和大致用途就够了，细节等讲内存管理时再展开。

## 7. 为什么这张图值得背下来

三个实际用途。

第一，回答面试题时用词准确。说"指令在代码段、已初始化的全局变量在数据段、未初始化的在 BSS 段、动态分配在堆、局部变量在栈"，比"静态区""全局区"专业得多。

第二，看到地址能猜出来源。`0x0804xxxx` 多半是代码或数据段，`0xb7xxxxxx` 附近是共享库，`0xbfxxxxxx` 是栈，`0x0` 附近是小数字崩溃——空指针加偏移。

第三，理解崩溃原因。空指针崩溃是因为保留区不可访问；改字符串字面量崩溃是因为 `.rodata` 只读；栈溢出是栈长到头了。这三类崩溃看着都像"段错误"，根因完全不同。

## 小结

- 32 位 Linux 的 4G 虚拟地址空间：0~3G 用户空间（进程私有）+ 3G~4G 内核空间（所有进程共享）
- 用户空间从低到高：保留区（0~0x08048000，让空指针必崩）→ `.text` → `.rodata` → `.data` → `.bss` → 堆（向上生长）→ 共享库 → 栈（向下生长）→ 命令行参数与环境变量
- `.data` 放"初始化且不为 0"的全局/静态变量；`.bss` 放"初值为 0 或未初始化"的，加载时由内核清零
- 局部变量不产生符号，编译期只为它生成一条写内存的指令；那 4 个字节是函数运行时在栈上开的
- `static` 局部变量在数据段，第一次执行到时才初始化，因此能跨调用保持值
- `.rodata` 与 `.text` 只读，改字符串字面量必崩
- 栈是每个线程独立的，代码段、数据段、堆由进程内所有线程共享
- 内核空间分 DMA / Normal / HighMem 三个 zone，进程间通信靠共享的内核空间（如匿名管道）

内功篇四讲到这里结束：这张内存地图是地基，函数调用在它的栈段上盖房子，编译链接决定了房子里的东西怎么摆。下一章开始进入 C++ 的语法细节——`const` 到底修饰谁、引用与指针的区别、`inline` 和重载背后的编译器行为。
