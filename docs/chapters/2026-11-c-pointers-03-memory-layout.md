# 变量到底住在哪里：C 的内存地图

![C 进程的虚拟地址空间布局](/assets/images/c-pointers/cptr-03-memory-layout.png)

写一个 C 程序，里面声明了全局变量、局部变量，还 malloc 了一块内存。程序跑起来，这些变量分别被安排在内存的什么位置？

如果你打印它们的地址，会发现一件怪事：全局变量的地址是 `0x601xxx` 这种"小号"，局部变量却是 `0x7fff…` 这种"大号"，malloc 出来的又不一样。这不是随机——**每个 C 进程的内存都被划分成几个固定片区，不同种类的变量各归其位。**

这一课我们把这张内存地图画出来。理解了它，"为什么局部变量用完就没了""为什么返回局部变量的地址是灾难"这类问题就全都有了答案。

### 1. 你看到的地址，其实是"假地址"

先做一个小实验。写个程序，打印一个全局变量的地址，然后让它循环等待输入：

```c
int hoge;

int main(void)
{
    printf("&hoge = %p\n", (void*)&hoge);
    getchar();            /* 停在这里，别退出 */
    return 0;
}
```

现在打开两个终端，**同时**运行这个程序。你猜两个程序打印的地址一样吗？

答案：一模一样。但两个程序里的 hoge 明明是两个独立的变量，各改各的互不影响。同一个地址怎么装两个变量？

因为它们打印的根本不是物理内存的地址，而是**虚拟地址（virtual address）**。

操作系统给每个进程发了一套独立的"门牌号系统"。进程 A 的门牌 100 和进程 B 的门牌 100，背后是两块完全不同的物理内存。操作系统和 CPU 联手做翻译，进程只管用自己的门牌号，不关心真正的内存在哪。

这么做的好处立竿见影：你的程序写错了地址，把内存写崩了，操作系统只会毙掉你这一个进程——隔壁的浏览器、编辑器毫发无损。**虚拟地址是现代操作系统给每个进程的沙盒。**

### 2. 一个实验，看清整张地图

光说不练假把式。我们把各种类型的地址一次性全打出来：

```c
#include <stdio.h>
#include <stdlib.h>

int global_var;                      /* 全局变量 */
static int file_static_var;          /* 文件内 static 变量 */

void func(void)
{
    int local_var;                   /* 局部变量（自动变量） */
    static int local_static_var;     /* static 局部变量 */
    printf("局部变量        %p\n", (void*)&local_var);
    printf("static局部变量  %p\n", (void*)&local_static_var);
}

int main(void)
{
    int *p = malloc(sizeof(int));    /* malloc 分配的内存 */

    printf("函数 func       %p\n", (void*)func);
    printf("字符串字面量    %p\n", (void*)"abc");
    printf("全局变量        %p\n", (void*)&global_var);
    printf("文件内static    %p\n", (void*)&file_static_var);
    printf("malloc 的内存   %p\n", (void*)p);
    func();
    free(p);
    return 0;
}
```

把输出按地址从小到大排一下（真实地址每次不同，但**相对位置是稳定的**）：

| 内容 | 地址（示例） | 片区 |
|---|---|---|
| 函数 func | 0x40057d | 只读区 |
| 字符串字面量 "abc" | 0x400760 | 只读区 |
| 文件内 static 变量 | 0x60104c | 静态区 |
| static 局部变量 | 0x601050 | 静态区 |
| 全局变量 | 0x601054 | 静态区 |
| malloc 的内存 | 0x1d12010 | 堆 |
| 局部变量 | 0x7fff7faef52c | 栈 |

片区归属一目了然：**代码和字符串字面量在低地址，静态变量紧挨着，malloc 的内存在中间（堆），局部变量在高地址（栈）。**

### 3. 四个片区，四种命运

逐个看看这四个片区的脾气。

**只读区（text/rodata）**：函数的机器码和字符串字面量住在这里，只能读不能写。往 `"abc"` 这样的字符串字面量里写数据，程序直接崩。函数代码也在这，反正没人需要改写正在跑的指令。

**静态区（data/bss）**：全局变量、static 变量的家。从程序启动到结束，它们的地址**固定不变**。这也是 static 局部变量"函数退出后值还在"的原因——它根本不住在栈上。

**堆（heap）**：`malloc` 分配的内存从这来。它的座右铭是"用完记得还"——`malloc` 申请、`free` 释放，由你全权管理。忘记 free 就是内存泄漏。堆的管理细节是下一课的主题。

**栈（stack）**：局部变量（自动变量）、函数参数、返回地址都住这。栈是这节课真正的主角，往下看。

### 4. 栈：函数调用的"托盘堆"

为什么局部变量要单独放一个区？看一个实验就明白了。

前面那个程序的输出里藏着一个惊人的细节：如果你让 `func()` 和另一个 `func2()` 都打印自己的局部变量地址，会发现**两个函数的局部变量地址完全相同**。

怎么做到的？因为局部变量的内存是**即用即取、用完即还**的：func() 被调用时拿到一块内存，返回时这块内存就被回收；随后 func2() 被调用，拿到的正好是同一块。

实现这个机制的，就是**栈（stack）**——一种"后进先出"的结构。你可以把它想象成一摞托盘：

![函数调用与栈帧：进入压一帧，返回弹一帧](/assets/images/c-pointers/cptr-03-stack-frame.png)

每调用一个函数，就在栈顶压入一块新托盘（叫**栈帧**，stack frame），里面装着这个函数的参数、局部变量、返回地址；函数一返回，托盘整层端走，栈顶缩回去，空间留给下一个函数。

这个设计一石三鸟：

- **省内存**：局部变量只在函数活着时占地方，几百个函数轮流用同一小块栈空间。
- **支持递归**：函数调用自己时，每一层都有自己独立的一帧。第 1 层的 `i` 和第 2 层的 `i` 是两个不同的格子，互不干扰。没有栈，递归根本没法实现。
- **自动管理**：不需要你操心分配和释放，进函数就有，出函数就没。

### 5. 经典灾难：返回局部变量的地址

理解了栈，就能看懂 C 里最高发的事故之一。

```c
/* 把 int 转成字符串返回 —— 这段代码有致命 bug */
char *int_to_str(int n)
{
    char buf[20];
    sprintf(buf, "%d", n);
    return buf;      /* 返回了局部数组的地址！ */
}
```

问题出在哪？`buf` 是局部变量，住在 `int_to_str` 的栈帧里。函数一 `return`，那层栈帧就被回收了——buf 那块内存已经不属于你了，随时会被下一个函数调用覆盖。

于是调用方拿到的指针，指向的是一块"随时可能被别人改写"的内存。运气好（没人马上用这块栈），内容暂时还在，程序看起来正常；运气不好，输出一串乱码。**这种 bug 最阴险：它不一定会立刻炸。**

那正确的做法是什么？三条路：

| 方案 | 写法 | 代价 |
|---|---|---|
| 调用方出缓冲区 | `void itoa2(int n, char *buf)` | 最简单，推荐；调用方负责提供内存 |
| static 局部变量 | `static char buf[20]` | 能跑，但两次调用互相覆盖，多线程更是灾难 |
| malloc 分配 | 函数里 malloc，调用方 free | 灵活，但引入"谁释放"的管理负担 |

记住这条铁律：**永远不要返回指向局部变量的指针。**

### 6. 栈溢出攻击：被写穿的返回地址

栈帧里，局部变量和**返回地址**（函数执行完该跳回哪里）是邻居。这就给了一种经典攻击以可乘之机。

如果栈上有个数组，而代码往里面写数据时不检查长度，写过头了会怎样？数据会顺着内存一路冲过去，先把相邻的局部变量踩烂，再往前就是**返回地址**。

```c
void vulnerable(void)
{
    char buf[16];
    gets(buf);    /* 不检查长度！输入超过 16 字节就开始踩别人的地盘 */
}
```

攻击者精心构造一串超长输入，把返回地址改写成自己恶意代码的地址——函数"返回"时，程序没有回到调用处，而是跳进了攻击者的代码。这就是**缓冲区溢出（buffer overflow）**，上世纪以来最臭名昭著的安全漏洞，没有之一。

正因如此，`gets()` 这个不做长度检查的函数已被 C11 标准除名。写代码时的教训只有一条：**凡是往栈上的数组写数据，必须自己检查长度**（用 `fgets` 代替 `gets`，用 `snprintf` 代替 `sprintf`）。

### 小结

- 进程用的是虚拟地址，每个进程一套独立门牌号，互不干扰
- 内存分四个片区：只读区（代码、字符串字面量）、静态区（全局/static）、堆（malloc）、栈（局部变量）
- 栈按"栈帧"管理：调用函数压一帧，返回弹一帧，空间自动复用——这就是局部变量用完就没的原因
- 永远不要返回局部变量的地址，那是指向"已回收托盘"的指针
- 栈上数组越界写会踩到返回地址，这就是缓冲区溢出漏洞的原理
