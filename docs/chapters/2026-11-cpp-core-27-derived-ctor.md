# 派生类的构造过程：基类部分请基类自己来

![派生类构造析构四步时序：基类构造 → 派生类构造 → 派生类析构 → 基类析构](/assets/images/cpp-core/cpp-core-27-derived-ctor.png)

上一篇结尾留了个问题：继承把基类的成员搬进了派生类的内存，那**谁**来初始化它们？最直觉的写法马上碰壁——在派生类构造函数体里给继承来的 `ma` 赋值，编译器报的错误居然是"**Base 没有合适的默认构造函数可用**"。

我要初始化 `ma`，编译器为什么扯到 Base 的构造函数上？这条报错信息正是本文的钥匙。它指向继承体系里最重要的一条分工原则：**派生类部分由派生类的构造/析构负责，基类部分由基类的构造/析构负责**——派生类没资格亲手初始化基类成员，只能"委托"。

边界：单继承、无虚函数的场景；多继承与虚继承的构造顺序在菱形继承篇补充；成员对象的构造顺序沿用第 12 篇的声明序规则。

## 1. 一行赋值引发的报错

例. 最小复现：

```cpp
class Base
{
protected:
    int ma;                          // protected：派生类能访问（第 26 篇）
public:
    Base(int data) : ma(data) { cout << "Base 构造"; }
    ~Base() { cout << "Base 析构"; }
};

class Derived : public Base
{
    int mb;
public:
    Derived(int data)
    {
        ma = data;                   // 意图：初始化继承来的 ma
        mb = data;
        cout << "Derived 构造";
    }
};

Derived b(10);
```

解. 编译错误落在派生类构造函数上：**Base 没有合适的默认构造函数可用**。

奇怪，报错说的不是 `ma` 不能赋值，而是"Base 没有默认构造"。翻译一下：编译器构造派生类对象时，先要构造其中的**基类部分**；构造基类部分的标准方式是调用基类构造函数；派生类的构造函数没有指定调哪个，编译器就按默认规则找 `Base` 的**默认构造**——而 `Base` 自己写了带参构造，默认构造已被挤掉（第 11 篇的规则），链条断在这里。

至于 `ma = data` 这行——`ma` 是 protected，**访问**没问题，但那已经是赋值不是初始化：赋值发生时基类部分必须已经构造完成，而它恰恰还没构造。**访问权限与初始化资格是两回事**，继承来的成员你看得见、摸不着（初始化层面）。

## 2. 分工原则：各管各的部分

把规则说完整。派生类从基类继承**所有成员——构造函数和析构函数除外**。基类部分成员的初始化与清理，指定由**基类自己的构造/析构函数**完成；派生类只负责自己新增的部分。

"除过构造析构"这条常被追问：到底有没有"继承构造函数"？较真的答法：构造析构不在继承名单上，但派生类**能调用**它们——在初始化列表里调基类构造，就是使用那份从基类来的接口。别在名词上钻牛角尖，记住行为就够了。

于是正确写法是在初始化列表里**显式委托**：

```cpp
Derived(int data) : Base(data)       // 委托基类构造函数初始化基类部分
{
    mb = data;                       // 函数体只管派生类自己的成员
    cout << "Derived 构造";
}
```

`: Base(data)` 是在说："基类那部分的初始化，请用 `Base(int)` 来做。"编译器照办，报错解除。

## 3. 四步时序：一次完整的生与死

派生类对象的完整生命周期是固定的四步：

```text
构造：
  ① 执行派生类构造函数的初始化列表 → 先调基类构造函数，基类部分就位
  ② 派生类构造函数体执行 → 派生类自己的成员就位
析构（作用域结束）：
  ③ 派生类析构函数执行 → 先释放派生类部分占的外部资源
  ④ 基类析构函数执行 → 再释放基类部分成员占的外部资源
```

两个顺序要点。**构造时基类先于派生类**：初始化列表在派生构造函数体**之前**执行（第 12 篇的时间线），所以 `Base 构造` 打印在 `Derived 构造` 之前——不写委托时编译器试图调的默认构造，也是排在函数体前面的同一个位置。

**析构与构造严格相反**：派生类部分先析构，基类部分后析构。这不是新规则，是第 11 篇"先构造的后析构"栈序原则在继承结构上的投影——基类部分在内存里"垫底"，它得等上面那层（派生类部分）收拾完才能拆。

跑一遍完整验证，输出正好四行：

```text
Base 构造 → Derived 构造 →（作用域结束）→ Derived 析构 → Base 析构
```

为什么析构顺序必须是这个方向？看资源归属就明白。假设基类有指针成员指向堆内存（占外部资源），这块内存的释放逻辑写在**基类析构函数**里。若先析构基类，派生类部分还在使用的资源就可能被提前回收；反过来，派生类先清完自己的，基类再收走自己那份，谁的资源谁负责，互不踩脚。

## 4. 三种基类构造的委托姿势

初始化列表里怎么写 `Base(...)`，取决于基类提供了什么：

```cpp
Derived(int d) : Base(d) {}          // 基类只有带参构造 → 必须显式委托，否则报错
Derived() {}                         // 基类有默认构造 → 可以不写，编译器自动调 Base()
Derived(int d) : Base(d), mb(d) {}   // 成员对象同理：显式指定构造方式（第 12 篇）
```

规律与第 12 篇完全同构——那里是成员对象（组合），这里是基类（继承），**"没指定构造方式就找默认构造"的规则一以贯之**：组合关系里是成员对象的默认构造，继承关系里是基类的默认构造，派生类构造函数的初始化列表是唯一能指定它们构造方式的地方。

析构函数没有参数、没有重载，派生类的 `~Derived()` 执行完后编译器**自动**接上 `~Base()`——析构从来不需要（也没办法）"显式委托"，顺序是死的：派生先、基类后。

## 小结

- 派生类继承所有成员**除构造和析构**；基类成员不能在派生类里直接初始化——访问权限（protected 可见）与初始化资格是两回事
- 分工原则：派生类构造/析构只管派生类部分；基类部分的生灭由基类构造/析构负责，派生类在初始化列表里显式委托 `: Base(data)`
- 四步时序：基类构造 → 派生类构造 →（作用域结束）→ 派生类析构 → 基类析构；初始化列表先于函数体，所以基类构造先行
- 析构与构造严格相反——"先构造的后析构"栈序原则在继承结构上的投影，保证谁的资源谁负责
- 基类无默认构造时必须显式委托；有默认构造时可省略（编译器自动调）；析构无需也无法显式委托，顺序编译器定死
