# 函数模板：把"类型"变成参数

![函数模板：调用点实例化生成模板函数；特例化与非模板函数的调用优先级](/assets/images/cpp-core/cpp-core-17-function-template.png)

写一个 `compare(int, int)` 比整数，再抄一遍 `compare(double, double)` 比小数，再抄一遍处理字符串——三份代码一个逻辑。函数模板把"抄"这件事交给编译器：你写一遍逻辑，把**类型**留成参数，调用时编译器按需生成各类型的版本。

模板的名词密度是 C++ 各主题里最高的：函数模板、模板函数、实例化、实参推演、特例化、非类型参数……一锅粥是常态。这篇用一条主线把它们全部串起来：**模板本身不编译，一切发生在调用点**。读懂这一句，名词全部归位，"模板为什么必须写在头文件里"这样的工程问题也顺带有了答案。

边界：类模板是下一篇的主题；模板元编程、变参模板不在本系列范围；非类型参数本文只作认识。

## 1. 复制粘贴三遍之后

例. 需求很简单：比较两个值的大小。C 的写法是类型写死：

```cpp
bool compare(int a, int b) { return a > b; }
```

解. 这个函数的形参 `a`、`b` 把**实参的值**参数化了——传什么值都行；但实参的**类型**被钉死成 `int`。要比较 `double` 就得再抄一份，要比较别的类型再抄——逻辑一份、类型三份。

模板把第二维也参数化：

```cpp
template<typename T>
bool compare(T a, T b)
{
    return a > b;
}
```

`template<typename T>` 声明了一个**类型参数** `T`，它不接收值，接收**类型**。调用时指定 `T=int`，编译器就用 `int` 替换模板里的 `T`，生成 `compare(int,int)` 那份代码——复制粘贴从此自动化。

`typename` 换成 `class` 也是合法的（老代码常见）：`template<class T>`。但 `class` 容易让人误以为 `T` 必须是自定义类类型（`int` 实例化明明也行），新代码建议统一 `typename`。

## 2. 模板本身不编译，一切发生在调用点

这是模板最重要的一条认知。`template<typename T> bool compare(T a, T b) { return a > b; }` 这一段，编译器**不会编译**——`T` 是什么类型都不知道，`a > b` 是比整数、比小数还是比对象？无从生成指令。

那什么时候编译？**函数调用点**。你写 `compare<int>(20, 30)` 时，编译器用 `int` 从原模板**实例化**出一份真正的函数：

```cpp
bool compare<int>(int a, int b) { return a > b; }   // 实例化产物，叫"模板函数"
```

区分三个名词的口诀：

- **函数模板**：`template` 开头的那段代码，是图纸，不编译；
- **实例化**：在调用点用具体类型从图纸生成代码的动作；
- **模板函数**：实例化的产物，真正的函数，被编译、进符号表。

模板名不能直接当函数名用——`compare(20, 30)` 之所以合法，是因为下面第 3 节的实参推演在帮忙；**模板名 + 实参列表**（`compare<int>`）才构成一个真正的函数名。

同一类型只实例化一份。第二次 `compare<int>(1, 2)` 不会重新生成——同一符号在符号表里只能出现一次（第 02 篇的规则），复用第一次的产物即可。

## 3. 实参推演：把"指定类型"省掉

`compare(20, 30)` 没写 `<int>`，也能编译——编译器根据**实参的类型**推演模板参数：两个 `int` 实参，`T = int`。这就是**模板实参推演**。

推演会翻车的场景也常见：

```cpp
compare(20, 10.5);       // 错误：T 不明确，可能是 int 也可能是 double
```

两个形参共用一个 `T`，一个实参 `int`、一个实参 `double`，编译器不知道听谁的。两条出路：

```cpp
template<typename T, typename E>
bool compare(T a, E b);          // 出路一：两个类型参数，各推各的

compare<int>(20, 10.5);          // 出路二：显式指定 T=int，double 实参转成 int
```

显式指定后，推演不再介入，`10.5` 按普通函数调用的规则转换成形参类型——转换不通就报错。

## 4. 特例化：编译器生成的版本不合适时

推演也有力不从心的时候。比较两个字符串：

```cpp
compare("abc", "abd");           // 推演出 T = const char*
```

实例化出的模板函数是 `const char*` 版的 `a > b`——比较的是**两个指针的地址大小**，完全不是你想的字典序。编译器没本事替你改逻辑，它只会忠实替换类型。

**模板的特例化**（specialization，也叫专用化）为此而生：开发者亲自为某个类型写一份实例化版本：

```cpp
template<>                                    // 尖括号空着，但不能省
bool compare<const char*>(const char* a, const char* b)
{
    return strcmp(a, b) > 0;                  // 字典序
}
```

`template<>` 表示"这份实例化也是从原模板来的"——先有模板才有特例化，没有模板就写特例化是语法错误；尖括号空着是因为类型已经写死。从此 `compare("abc","abd")` 走这份自定义版本。STL 几乎给每个容器的模板都提供了 `const char*` 的特例化，原因正在于此：字符串的操作逻辑与一般类型不同。

## 5. 三者共存，谁优先

同一个名字 `compare` 下可以同时存在三样东西：函数模板、模板的特例化、同名**非模板函数**（普通函数）。很多资料把这种共存称为重载，姑且按共存理解。调用时编译器的选择顺序是：

> **非模板函数 > 特例化 > 从模板实例化。**

`compare("abc", "abd")` 三方都接得住时，编译器选**非模板函数**——直接调用现成函数最省事，不用推演不用实例化。没有非模板版本，才看有没有特例化；连特例化也没有，才自己动手从原模板实例化。

想强制走模板路径也有办法：给模板名加实参列表。`compare<const char*>("abc","abd")` 里，普通函数名后面不可能跟尖括号，编译器只能把它当模板处理，查到特例化就用特例化。

## 6. 模板为什么必须住在头文件里

多文件工程把模板定义放 `.cpp`、声明放 `.h`，另一个 `.cpp` 里调用——链接器报"无法解析的外部符号"。原因还是那条主线：模板不编译，**调用点才实例化**。调用方文件在编译时确实生成了 `compare<int>` 的未定义符号（und），等着链接；可定义方文件里从来没有谁调用过 `compare<int>`，于是没有任何模板函数被实例化、没有任何符号被定义——两边一对不上，链接失败。

正规解法因此只有一个：**模板的全部代码放头文件里**，哪个源文件要用就 `#include` 进来——调用之前必然看得到模板定义，实例化在任何文件里都能完成。这就是为什么 STL 全是头文件：`#include <vector>` 看到的就是源码本身。

应急办法也有：在定义文件里写**显式实例化定义**，命令编译器"不管有没有人调用，用指定类型立刻实例化"：

```cpp
template bool compare<int>(int, int);            // 强制生成 int 版本
template bool compare<double>(double, double);
```

链接于是有了符号。但类型没法穷举，这只是没有办法的办法——工程实践永远选头文件。

## 小结

- 模板参数化的是**类型**：一套逻辑，调用点用指定类型或推演类型实例化出各类型的版本
- 函数模板（图纸，不编译）→ 调用点实例化 → 模板函数（产物，才被编译）；同类型只实例化一份
- 模板名 + 实参列表才是函数名；`compare(20,30)` 能省尖括号靠实参推演；两实参类型不同时推演失败，需多类型参数或显式指定
- 编译器实例化的版本逻辑不合适（如 `const char*` 比地址）时，提供 `template<>` 特例化
- 三者共存选择顺序：非模板函数 > 特例化 > 模板实例化；`compare<T>(...)` 可强制走模板
- 模板代码放头文件：调用点实例化的机制决定了定义必须对调用方可见；显式实例化只是应急
