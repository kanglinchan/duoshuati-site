# 函数调用堆栈：一次调用在栈上留下了什么

![函数调用堆栈：参数、返回地址、旧 ebp、局部变量，自高地址向低地址依次排开](/assets/images/cpp-core/cpp-core-01-stack-frame.png)

有个同学拿一段代码来问我，说他在 `sum` 里打印了局部变量 `tmp` 的地址，回到 `main` 之后再去读这个地址，值就变了，在 Debug 版里干脆变成 `0xCCCCCCCC`。

我让他打开 VS 的"调用堆栈"窗口。两层：`main` 那一层有它自己的 `a`、`b`、`ret`，`sum` 那一层有形参 `a`、`b` 和局部变量 `tmp`。他说：`main` 和 `sum` 里都写了 `a`、`b`，内存里是不是各存了一份？

这就是本文要讲清的东西。先提两个我在面试里问过很多次的问题。

第一个：`main` 调用 `sum`，`sum` 执行完了，它怎么知道该回到 `main`？

第二个：回到 `main` 之后，它又是怎么知道从**哪一条指令**继续往下跑，而不是从头再跑一遍？

这两个问题都能用一句话回答：`call` 指令把返回地址压进了栈。但真要讲清楚"压进栈的到底是什么、压在哪儿、谁负责清掉"，就得把栈帧拆开看。

这篇文章我做的事是：拿五行 C++ 代码，把它的汇编一条一条念下来，让你看清一次函数调用在栈上到底留下了什么。读完你应该能对着 VS 的反汇编窗口或 `objdump` 的输出，自己说出每条指令在动哪块内存。

先划边界。本文所有寄存器、偏移量、地址都以 **32 位 x86** 为准（`esp` / `ebp`；32 位 Linux 的 `.text` 从 `0x08048000` 起，64 位则是 `0x400000` 起）。64 位和 ARM 的传参规则不同（x64 前几个参数走寄存器），本文不涉及。编译器优化开到 `-O2` 之后，很多栈帧会被优化掉，本文也不涉及——我们看的正是"没被优化"的那一版。

## 1. 待解剖的对象

例. 一段谁都写过的代码。

```cpp
#include <cstdio>

int sum(int a, int b)
{
    int tmp = 0;
    tmp = a + b;
    return tmp;
}

int main()
{
    int a = 10;
    int b = 20;
    int ret = sum(a, b);
    printf("ret = %d\n", ret);
    return 0;
}
```

解. 别急着看答案，先自己回答：从 `main` 执行到 `printf`，栈上多了几样东西？

四样外加一大块：两个实参（各 4 字节）、一个返回地址（4 字节）、一个旧 `ebp`（4 字节），以及 `sum` 自己用一条 `sub esp, 4Ch` 开出来的局部空间（76 字节）。它们从高地址往低地址紧挨着排下来。

## 2. 栈：一块从高地址往低处长出来的内存

栈（stack）这个结构只需要两个指针就能描述：栈顶和栈底。在 x86 上它们有专门的名字。

- `esp`（stack pointer）永远指向当前栈顶，也就是**最下面**那个用过的字节。
- `ebp`（base pointer）钉住当前函数栈帧的底部，函数运行期间它不动。

注意方向。栈是**从高地址向低地址生长**的：`push` 一次，`esp` 减小 4；`pop` 一次，`esp` 加回 4。所以后面看到 `[ebp-4]`、`[ebp+8]` 这种写法时，减号那边是低地址——那是函数自己的地盘，加号那边是高地址——那是调用者留下的东西。

## 3. 局部变量：为什么是 ebp-4

先看 `main` 里的第一行：`int a = 10;`。

在 VS 的反汇编窗口里，它可能显示成 `mov dword ptr [a], 0Ah`，看着很贴心。切成"显示符号名"关掉之后，真身就露出来了：

```asm
mov dword ptr [ebp-4], 0Ah     ; a = 10
mov dword ptr [ebp-8], 14h     ; b = 20
```

两个信息。

第一，**普通局部变量不产生符号**。栈上没有哪个格子叫 `a`，只有"`ebp` 减 4 的那 4 个字节"这个位置。你在反汇编里看到的变量名，是编译器额外塞给你的阅读便利，不是机器看到的东西。

第二，访问局部变量全靠 `ebp` 加偏移。为什么是减？因为 `ebp` 指着帧底，而帧底在高地址一侧，往上（低地址）走就要减。`a` 第一个放进去，占 `ebp-4`；`b` 接着放，占 `ebp-8`；第三行 `int ret` 自然占了 `ebp-0Ch`。

注意 `ret` 这会儿还没有值，它的初值要等 `sum` 算完才填进来。

## 4. 传参：从右往左压

到了第三行 `int ret = sum(a, b);`。函数调用要做的第一件事是准备参数——按 C 的调用约定（cdecl），实参**从右往左**压栈。

第一个进去的是 `b`：

```asm
mov eax, dword ptr [ebp-8]     ; 取出 b 的值 20
push eax                       ; 压到栈顶
```

`push` 之后，`esp` 减 4，那段新内存里躺着 20。这块内存从此刻起就是 `sum` 的形参 `b`。

接着轮到 `a`：

```asm
mov eax, dword ptr [ebp-4]     ; 取出 a 的值 10
push eax
```

再压 4 字节，`esp` 又减 4。

这里有个常被误会的地方：`int a = 10` 用的是 `mov`，不是 `push`。mov 只是往某个确定地址写值，栈顶指针不动；`push` 才是"把值放到新栈顶"。两者看起来都像"往栈上放东西"，实际动作完全不同。

那形参的内存是谁开的？是**调用方**开的。`main` 压完这两个值再去 `call`，`sum` 一进门就已经有这两个参数了，它自己不负责为形参分配空间。

那么，为什么非得从右往左压？从左往右压，栈上不也一样有两个数吗？

单看 `sum(a, b)` 确实看不出区别——两个固定参数，怎么排都能算对偏移。差别要等**可变参数函数**出场才显现。

`printf(const char* fmt, ...)` 的参数个数在编译期未知。`printf("%d %d", x, y)` 传三个，`printf("%s", s)` 传两个。函数体内部怎么找到第一个可变参数？

它靠 `fmt` 的位置：`fmt` 在 `[ebp+8]`，第一个可变参数在 `[ebp+0Ch]`，第二个在 `[ebp+10h]`……偏移是固定的，可以一路往后扫。

这个"固定偏移"能成立，前提是**第一个参数紧贴返回地址、落在最低地址**。

从右往左压正好满足：最后压进栈的 `fmt` 离 `ebp` 最近。反过来从左往右压，`fmt` 会被压到最高地址，它的偏移就取决于"这次一共传了几个参数"——而这个数字调用方临时才知道，函数自己无从得知，`[ebp+8]` 也就读不到格式串了。

所以这条约定不是随手定的，是给可变参数留的口子。你写普通函数时，只是顺带遵守它。

> **边界：** 64 位下前 6 个整型参数走寄存器（`rdi`、`rsi`…），可变参数另有规则，本文不涉及。

## 5. call 做了两件事

参数就位，轮到 `call sum`。

`call` 是个复合指令，它一次干两件事：

1. 把**下一条指令的地址**压栈。下一条指令是 `add esp, 8`（调用返回后清理参数的指令）。
2. 把 `eip` 改成 `sum` 的入口地址，跳过去。

为什么非要压这个地址？因为 `sum` 执行完必须知道回哪儿。这就是文章开头第二个问题的答案：返回地址不在别处，就在栈上，紧挨着最后压进去的那个实参（也就是最左边的 `a`）。

压完之后 `esp` 再减 4，此时栈的样子是（从低地址往高地址看）：局部变量、旧 ebp、返回地址、实参 a、实参 b。

## 6. 进门三条指令

跳进 `sum` 之后，先执行的不是 `int tmp = 0`，而是三条你可能在反汇编里见过但没细想的指令：

```asm
push ebp              ; 先把 main 的 ebp 存起来
mov  ebp, esp         ; 让 ebp 指向新的帧底
sub  esp, 4Ch         ; 一次性开出局部变量空间
```

第一步 `push ebp` 保存的是调用者的帧底，等 `sum` 返回时要还回去。

第二步 `mov ebp, esp`。x86 的 `mov` 从右往左读：把 `esp` 的值赋给 `ebp`。此刻 `esp` 停在刚压进去的旧 `ebp` 上，于是 `ebp` 也指向那儿——**旧 ebp 所在的位置，就是新栈帧的帧底**。

第三步 `sub esp, 4Ch` 把栈顶一次性往下挪 `0x4C`（76 字节）。为什么一次开这么多？因为编译器提前算好了这个函数所有局部变量加临时对象需要多少空间，一条指令全留出来，比每个变量 `push` 一次快得多。这个数字随函数内容变化，函数里多几个局部变量，它就跟着变大。

在 Windows + VS 的 Debug 版本里，这 76 字节还会被一段循环指令填成 `0xCC`。你在调试器里看到的 `0xCCCCCCCC` 就是这个东西，它是一道警戒线：读到这个值说明你用了没初始化的局部变量。把它当有符号整数打印出来，就是 `-858993460`。

GCC / G++ 不干这件事，所以同一份代码在 Linux 上编出来，栈里是上一轮调用留下的残留值——看起来有值，其实是垃圾。

还记得第 3 节里那句"局部变量靠 ebp 减偏移访问"吗？现在偏移的理由更清楚了：`ebp` 往下（低地址）是本次调用的局部变量和临时空间，往上（高地址）依次是旧 `ebp`、返回地址、实参。所以形参在 `sum` 眼里是 `[ebp+8]` 和 `[ebp+0Ch]`，返回地址是 `[ebp+4]`，旧 `ebp` 正好在 `[ebp]`。

一个函数里加一个局部变量，`sub esp` 后面那个数字就跟着变——这就是局部变量"占地方"的具体样子。

## 7. 返回：三步拆房

`sum` 算完，返回值放在 `eax` 里（这是 x86 的约定，返回值走寄存器不回栈）。然后收尾：

```asm
mov esp, ebp      ; 栈顶直接拽回帧底，局部变量空间一次性作废
pop  ebp          ; 弹出旧 ebp，ebp 恢复成 main 的帧底
ret               ; 弹出返回地址，跳回 main 的 add esp, 8
```

`mov esp, ebp` 是这套机制里最省事的一步：不用逐个释放局部变量，把栈顶指针一拽，那 76 字节当场就不属于你了。这也是为什么"函数返回后局部变量就没了"——不是被擦掉了，是没人认领了。

回到 `main`，最后一条 `add esp, 8` 把两个实参弹掉，`esp` 回到调用前的位置，栈彻底恢复原样。

到这里，开头两个问题都有答案了：回哪儿靠 `call` 压的返回地址；回哪儿之后从哪继续，靠 `ret` 弹出的那个地址。整件事没有任何魔法，全是 `esp` 和 `ebp` 两个指针在动。

## 8. 这个机制解释了两件旧事

第一件：为什么不能返回局部变量的地址。

```cpp
int* bad()
{
    int x = 42;
    return &x;      // 返回的是 [ebp-4] 这个地址
}
```

`x` 住在 `bad` 的栈帧里，也就是 `ebp-4`。函数一返回，`mov esp, ebp` 把那片空间还了回去；下一个被调用的函数压参数、开局部变量，随时可能把 `0x2A` 覆盖掉。你手里那个指针没失效（地址还是那个地址），但它指向的内容已经不是你的了。

第二件：为什么递归太深会栈溢出。

每次调用都要压参数、压返回地址、开局部空间，栈的总大小是有限的（Linux 默认 8MB 左右）。递归函数不返回，栈帧就一直往上叠，叠到撞上栈的边界，程序就崩了。栈溢出不是"内存不够"，是"这一块内存用完了"。

## 小结

- 栈从高地址向低地址生长，`push` 让 `esp` 减 4，`pop` 让它加 4
- 局部变量不产生符号，靠 `ebp` 减偏移访问；`ebp` 钉住帧底，函数运行期间不动
- 实参从右往左压栈，形参的内存由**调用方**开好
- `call` = 压返回地址 + 跳转；返回地址就在 `[ebp+4]`
- 进函数先 `push ebp` / `mov ebp, esp`，再 `sub esp, n` 一次开出局部空间
- 返回时 `mov esp, ebp` / `pop ebp` / `ret`，调用方再用 `add esp, n` 清参数
- 返回值走 `eax`，不占栈；局部变量随栈帧一起作废，所以不能返回它的地址
