# inline 与形参默认值：围绕一次函数调用的两处精打细算

![inline 在调用点展开代码省掉调用开销；形参默认值让未传的实参直接 push 立即数](/assets/images/cpp-core/cpp-core-08-inline-default.png)

还记得第 01 篇里那个 `sum` 函数吗？它这次要再被榨一遍。这个函数的函数体只有三条指令：一条 `mov` 取数、一条 `add` 相加、一条 `mov` 把返回值放进 `eax`。可我们调用它一次，付出的指令远不止三条——压参数、压返回地址、建栈帧、拆栈帧，每一项都比函数本体贵。

"函数太简单又调用太频繁"这个场景，引出了本文的两个主角。`inline` 从**调用方**省钱：直接把函数体展开到调用点，整个调用过程消失。形参默认值从**被调方**省钱：少传的实参不用取变量、直接压立即数，还省一条取数指令。

面试里"inline 和普通函数的区别"出现频率极高，多数人只答一句"省了函数调用开销"。这篇文章带你把答案铺成四层，再顺手把形参默认值的三条规矩从汇编层面讲明白。

边界：inline 的展开效果以 MSVC Release 和 GCC `-O1` 以上为准；Debug 版的行为单独说。默认值部分只讲普通函数，成员函数的默认值在构造函数篇还会见面。

## 1. 先算账：调用开销比函数本体贵多少

例. 还是最初那个函数。

```cpp
int sum(int a, int b)
{
    return a + b;
}
```

解. 第 01 篇拆过它的完整调用：两个实参 `push` 进栈，`call` 压返回地址，进门 `push ebp` / `mov ebp, esp` / `sub esp` 建帧，出门 `mov esp, ebp` / `pop ebp` / `ret` 拆帧，回来再 `add esp, 8` 清参数。

十来条指令的固定开销，服务的是三条指令的本体。这笔账在循环里会滚雪球：循环一千万次做 `x + y`，绝大部分时间花在进栈出栈上，真正的加法反而成了零头。

函数体大的时候没这个问题——几百行的函数，调用开销只是芝麻。问题专挑"**函数极简 + 短时间内大量调用**"这个组合下手。inline 就是为此准备的。

## 2. inline：在编译期把调用点整个抹掉

内联函数的处理发生在**编译阶段**：编译器看到 `sum(10, 20)` 时，不做函数调用，直接把函数体代码抄到调用点，等效于把 `a + b` 原地写了一遍。

效果有两层。第一层，那十来条开销指令没了，`call`、建帧、拆帧全部消失。第二层容易被忽略：**内联成功的函数不会在符号表里生成符号**。没有调用，就没有对这个函数的引用需求，符号表里根本不出现 `sum`。

验证方法在 Linux 上一条命令就能做：`g++ -O1 main.cpp` 编译后用 `objdump -t` 查符号表——`sum` 这个符号找不着了，说明它真被内联了。反过来，符号还在，就说明编译器没接受这次内联。

## 3. inline 是建议，不是命令

在函数前写 `inline`，语义是"建议编译器按内联处理"，**最终裁决权在编译器**。两种函数无论怎么写都内联不了：

**递归函数不可能内联。** 展开多少层，要等运行时才知道递归条件何时结束；编译器不执行指令，它算不出这个数字，自然无法在编译期抄写一个未知次数的自己。

**函数体太大不内联。** 五六十行的函数强行在每个调用点展开，代码体积暴涨，指令缓存的代价很快超过省下的调用开销；展开处的局部名字也可能与调用处冲突。编译器会礼貌地拒绝这个建议。

还有一个版本坑：**Debug 版本里 inline 完全不生效**。调试需要"跟进去看函数的栈帧"，真展开了就没函数可进。所以 MSVC 的 Debug 调试配置下，inline 函数照样有标准的 `call` 过程；只有 Release（或 GCC 提高 `-O` 级别）才真展开。你在调试器里看到内联函数还有压栈指令，不要奇怪，是版本原因，不是编译器出错。

顺带一句和宏的比较：`#define ADD(x,y) ((x)+(y))` 也能做到调用点展开，但没有类型检查、不进符号表、副作用参数会被展开多次。inline 函数是带完整类型系统的宏替代品，这也是它存在的第二个理由。

## 4. 面试标准答案：四层递进

"inline 和普通函数的区别"按这四层答，广度深度都有了：

1. **调用开销**：普通函数调用有标准开销（压参、压返回地址、建帧拆帧）；inline 在编译期把函数体在调用点展开，开销消失；
2. **符号表**：内联成功则不生成符号，可以用 `objdump -t` 验证；有符号说明没内联成功；
3. **只是建议**：递归函数无法内联，函数体过大编译器拒绝，最终由编译器决定；
4. **版本差异**：Debug 下 inline 不生效，调用过程与普通函数一致；Release 才真正展开。

## 5. 形参默认值：压栈指令的三种形态

第二个主角登场。给形参配默认值后，实参可以少传：

```cpp
int sum(int a, int b = 20);

sum(10);         // b 用默认值 20
sum(10, 30);     // 传了就用传的
```

很多人以为"有默认值就都不压栈了"。看汇编就明白：**形参依然要压栈**，只是来源不同。三种调用的压栈指令对照：

- `sum(10, 30)`：实参是立即数，`push 1Eh`、`push 0Ah`，然后 `call`；
- `sum(x, y)`（传变量）：每多一步 `mov eax, [ebp-8]` 从变量内存取值，再 `push eax`；
- `sum(10)`（缺省 b）：没传的那个直接 `push 14h`——默认值是立即数，压栈指令反而比传变量**少一条 mov**。

所以默认值版本的效率账是：传立即数时与普通调用完全相同；少传时省下取变量那条指令。单次省一条看不出什么，循环里调用一百万次，差距就累积出来了。这条省出来的指令也是"立即数不占内存、直接躺在指令里"这个事实的一次现身说法。

## 6. 三条规矩：从右向左，只出现一次

默认值有三条硬规矩，笔试常出。

**规矩一：给默认值必须从右向左。** `int sum(int a, int b = 20)` 合法，`int sum(int a = 10, int b)` 非法。原因还是那个压栈顺序：调用时实参从左往右对应形参，压栈从右往左进行。假如允许"a 有默认、b 没有"，调用就得写成 `sum(, 5)`——跳过第一个参数——语法上根本不存在这种写法。右边有默认、左边没有，才与"从左往右给参"兼容。

**规矩二：同一个形参的默认值只能出现一次。** 定义处可以给，声明处也可以给，但两处都给同一个形参就报错——哪怕两处的值一模一样：

```cpp
int sum(int a, int b = 20);      // 声明给 b
int sum(int a, int b = 20) { }   // 定义再给 b：错误，重定义默认参数
```

函数声明可以写无数次，定义只有一次，但默认值不管出现在声明还是定义里，每个形参只许给一次。

**规矩三：从上到下看，默认值的出现顺序必须从右向左。** 编译器从上往下读代码，读到某一行时它必须已经知道右边形参的默认值，才能接受左边新出现的默认值。所以"声明给 `b`、定义再给 `a`"是合法的：

```cpp
int sum(int a, int b = 20);      // 先右
int sum(int a = 10, int b) { }   // 后左，合法
```

三条规矩合成一句话：默认值沿着形参列表**从右往左、只给一次、从上往下不许回头**。

> **边界：** 默认值是编译期行为，压进栈的是具体数值，不占运行时开销；虚函数的默认值有静态绑定的坑，属于继承篇的内容，本文不涉及。

## 小结

- 函数调用开销固定十来条指令，函数体越简单、调用越频繁，开销占比越重
- inline 在编译期把函数体展开到调用点：开销消失，符号表不生成符号，`objdump -t` 可验证
- inline 只是建议：递归函数无法内联，函数体过大被拒绝；Debug 版一律不生效，Release 才展开
- 面试四层答案：调用开销、符号表、只是建议、版本差异
- 形参带默认值依然压栈；缺省参数直接 `push` 立即数，比传变量少一条 `mov`
- 默认值从右向左给；同一形参只出现一次（声明定义合计）；从上到下出现顺序从右向左
