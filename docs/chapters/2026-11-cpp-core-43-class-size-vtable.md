# 类大小与虚表大小：虚函数到底"贵"在哪

![虚函数/虚继承对对象大小的影响：vfptr/vbptr 各 +4；虚函数个数只影响虚表大小不影响对象](/assets/images/cpp-core/cpp-core-43-class-size-vtable.png)

"一个类里有 3 个虚函数，对象多大？"——这道题的正确答案让很多人意外：**和 0 个虚函数一样大**（都只多一个 vfptr）。虚函数的"贵"，贵的地方跟多数人想的不一样。

上一篇的 sizeof 算法加上指针分量（vfptr/vbptr）就完整了。这一篇专攻"指针分量"的记账规则：什么时候多指针、多几个、虚函数个数影响谁——最后一篇，把对象大小的账本合上。

边界：32 位下指针 4 字节、64 位（x64）下 8 字节——文中所有数字以 32 位为准，末尾给 64 位的换算；多继承下多个 vfptr 的排布属于多继承话题，不展开。

## 1. 两条铁律：对象只认"指针个数"，不看"函数个数"

虚函数体系对对象大小的影响，浓缩成两条铁律：

> **铁律一：类里有虚函数（自己定义的或继承来的），对象头部多一个 vfptr，+4 字节。**
> **铁律二：虚函数的个数不影响对象大小，影响的是虚函数表的大小。**

推导用的是第 29 篇的内存模型：对象头部只需要**一根指针**指向本类型的虚函数表；虚函数的地址都住在**表**里，表是类型级别的、全体对象共享——多一个虚函数只是表里多一项，对象纹丝不动。

```cpp
class A { virtual void f1() {} };                        // 4
class B { virtual void f1() {} virtual void f2() {}
          virtual void f3() {} };                        // 还是 4！
```

A 和 B 的对象都是 4 字节（只有一个 vfptr），差别在 B 的虚函数表比 A 的多两项。面试答这题的完整句式：**"虚函数个数不影响对象大小，只影响虚函数表大小——对象里永远只有一根 vfptr。"**

虚继承的 vbptr 同理：每个"虚继承了的基类子对象"位置补一根 vbptr（第 32 篇），单路虚继承 +4。它是对象大小里第二类指针分量。

## 2. 组合记账：三个状态的 sizeof 全推导

把 vfptr、vbptr、成员变量、对齐四样放在一起，跑一遍完整推导：

```cpp
class Empty {};                                   // 1（空类保底，第 42 篇）
class WithV : public Empty {                      // 继承空类 + 虚函数
    virtual void f() {}
};                                                // 4：vfptr（空类保底被 vfptr 覆盖）
class WithVAndV : virtual public Empty {          // 虚继承 + 虚函数
    virtual void f() {}
};                                                // 8：vfptr + vbptr
```

第三个类看着"什么成员都没有"，对象却要 **8 字节**——两根指针各占 4。这是面试题原题："空类 + 虚继承 + 虚函数，多大？"答案的分解必须讲清：**不是 1+4+4=9，而是 vfptr 4 + vbptr 4 = 8，再按最大成员（指针 4）对齐——恰好 8**。空类的 1 字节保底在有指针分量时不再单独出现（指针已经提供了可构造的地址）。

再加虚函数呢？`virtual void f1(); virtual void f2(); virtual void f3();` ——**还是 8**。铁律二再次生效：三个虚函数让虚函数表长到三项，对象里的 vfptr 还是那一根。

## 3. 汇总：对象大小的完整账本

上一篇 + 本篇的规则合龙，任何类的 sizeof 都能按这张清单推导：

| 计入项 | 大小（32 位） | 说明 |
|---|---|---|
| 非静态成员变量 | 各自大小 | 按对齐算法摆放（第 42 篇） |
| vfptr | +4 | 有虚函数（含继承来的）就有，**只有一根** |
| vbptr | 每个虚继承基类 +4 | 虚继承才有 |
| 对齐补位 | — | 总大小按最大成员（含指针）对齐 |
| **不计入** | — | 静态成员变量、成员函数、虚函数表本体 |

最后一样特别强调：**虚函数表本身不占对象的内存**。它在只读数据段（.rodata），全类一份，程序启动即加载、伴随整个生命周期（第 29 篇）。对象越大越"贵"的是内存占用，虚表越大越"贵"的是只读段空间——两本账分开记。

## 4. 换算到 64 位

x64 下指针 8 字节，所有"指针分量"翻倍：vfptr +8、vbptr +8、`WithVAndV` 变 16。成员变量的大小不变（int 还是 4、double 还是 8），但对齐基准可能被指针抬高——char + vfptr 在 32 位是 8，在 64 位是 16。

面试若追问 64 位，答案句式：**"所有指针分量翻倍，成员大小不变，对齐基准可能被指针抬高。"**一句话覆盖全部变化。

## 5. 一点成本观：虚函数到底贵不贵

把账本算完，可以给"虚函数的性能代价"一个公允的说法。**空间上**：每对象 +4（一根指针），每个类一张表——绝大多数场景可忽略。**时间上**：动态绑定三条指令（取 vfptr → 查表 → call）比静态绑定的一次 call 多两条，且虚函数通常无法内联（调用点编译期不知道目标）——热点路径上 measurable，普通业务里无感。

真正要警惕的不是"用不用虚函数"，而是第 24 篇那类事故（迭代器失效、对象切片）和第 21 篇那类错误（混用 new/delete）。虚函数的空间代价是**确定性的小额支出**，换来的是第 30 篇的开闭原则——这笔交易在整个 C++ 工程实践里几乎永远划算。

## 小结

- 铁律一：有虚函数（含继承来的）对象 +vfptr（4 字节）；虚继承 +vbptr（每路 4 字节）
- 铁律二：虚函数个数不影响对象大小、只影响虚函数表大小——对象里永远只有一根 vfptr
- 空类 + 虚继承 + 虚函数 = 8（vfptr 4 + vbptr 4，按指针 4 对齐）——"三个虚函数还是 8"
- 完整账本：非静态成员 + vfptr + vbptr + 对齐补位；静态成员、成员函数、虚表本体都不计入
- 64 位换算：指针分量翻倍，成员不变，对齐基准可能被指针抬高
- 虚函数的成本观：每对象 +4、查表多两条指令、无法内联——确定性小额支出换开闭原则，划算
