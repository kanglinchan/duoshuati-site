# 类和对象：一套成员方法怎么伺候一万个对象

![对象各自持有成员变量，成员方法只有一份在代码段，靠编译器塞进来的 this 指针区分调用者](/assets/images/cpp-core/cpp-core-10-class-object-this.png)

`good1.show()` 打印出"面包 20.5 元"，`good2.show()` 打印出"空调 10000 元"。两个调用执行的是**同一个函数**，代码段里只有一份 `show` 的指令，它凭什么第一次读面包的数据、第二次读空调的数据？

这个问题的答案就是 `this` 指针。但直接背"this 指向当前对象"没有意义——这篇文章从 OOP 的出发点讲起，把类、对象、封装、对象大小一路铺到 `this`，让你能推出来"为什么必须有这个指针"，而不是记住它。

边界：本文以一个商品类贯穿；构造函数、析构函数是下一篇的主题；内存对齐的完整规则（指定对齐、packed）在第 42 篇展开，这里只讲默认规则。

## 1. OOP 的出发点：从实体到类

用面向对象解决问题，第一步不是写 `class`，是**分析问题场景里有哪些实体**。做商品管理系统，场景里的实体是"商品"；做人员管理系统，实体是学生、老师、班主任。

找到实体后，从两个维度拆它：

- **属性**：名称、单价、库存数量——实体"有什么"；
- **行为**：展示信息、修改价格——实体"能做什么"。

这两个维度合起来叫 **ADT**（Abstract Data Type，抽象数据类型）。把 ADT 翻译成代码：属性输出为**成员变量**，行为输出为**成员方法**：

```cpp
class CGoods
{
private:
    char m_name[20];        // 属性 → 成员变量
    double m_price;
    int m_amount;

public:
    void init(const char* name, double price, int amount);   // 行为 → 成员方法
    void show();
};
```

类名带大写 `C` 前缀、成员变量带 `m_` 前缀，都是为了让读代码的人一眼分清"这是个类""这是成员变量"——规范不改变语义，改变的是可读性。

有一组关系要咬清楚：**类是实体的抽象类型，对象才是实体本身**。`CGoods` 这个类型不占内存，就像"商品"这个概念不占货架；`CGoods good1;` 实例化出来的 `good1` 占内存（在栈上），它才对应柜台上那一袋面包。一个类可以实例化无数个对象，就像一个概念可以对应无数个实体。

## 2. 封装：属性私有，行为公开

上面的代码里出现了两个访问限定符：`private` 和 `public`（还有第三个 `protected`，继承篇再讲）。C++ 的默认访问属性是 `private`——类不加限定符的成员外部摸不到。

标准做法是一条铁律：**属性全部私有，对外只提供公有的方法**。直接写 `good1.m_price` 编译报错"无法访问 private 成员"，想读想写都得走方法：

```cpp
void setPrice(double price)        { m_price = price; }
double getPrice() const            { return m_price; }
```

为什么要绕这一道？因为方法可以加检查、加日志、加锁，属性的可控性从"谁都能碰"变成"只有我批准的路径能碰"。这就是封装——OOP 四大特征（抽象、封装、继承、多态）里的第二个。

`get` 方法还有个细节值得停一下。获取名称如果写成 `char* getName() { return m_name; }`，外部拿到这个普通指针就能 `strcpy` 改掉私有数组——封装被一个返回值漏了个底朝天。所以返回只读的：

```cpp
const char* getName() const        { return m_name; }
```

第 06 篇讲过"常量的地址不能泄露给普通指针"，这里是同一个原则在接口设计上的应用：私有数据的地址，只能以 `const` 的形式出去。

> **边界：** 类内定义的成员方法会被编译器自动按内联处理（第 08 篇的规则）；要在类外定义，必须加作用域 `void CGoods::show() { ... }`——`CGoods::` 写在**方法名前面**，不是返回值前面，写错位置就成了一个普通全局函数。

## 3. 对象多大：只数成员变量，不看成员方法

`sizeof(CGoods)` 是多少？40。这个数字只由成员变量决定，**成员方法再多、再长，都不占对象的内存**。

计算过程就是结构体对齐那套（第 01 篇讲过栈上变量按声明排布，规则相同）：找占字节最长的成员作对齐基准——`m_price` 是 `double`，8 字节，整个对象按 8 对齐：

```text
m_name    char[20]     偏移 0~19
（补 4 字节凑齐 24，让 double 落在 8 的倍数上）
m_price   double       偏移 24~31
m_amount  int          偏移 32~35
（补 4 字节，让总大小凑成 8 的倍数）
────────────────────────────
总计 40 字节
```

两处补位（padding）都是为了让每个成员的偏移落在自身大小的整数倍上、总大小落在最大对齐值的整数倍上。对齐的收益是 CPU 访问内存的次数变少——不对齐时一个 `double` 可能横跨两个缓存行，读它要两次 IO。

不想手算，VS 自带查看器。在 VS 命令提示符里切到源码目录：

```text
cl /d1reportSingleClassLayoutCGoods 文件名.cpp
```

它会打印 `CGoods` 的完整内存布局：每个成员的偏移、补位位置、总大小。拿本文的例子验证一遍，40 字节一目了然。

## 4. this 指针：编译器塞进来的隐含形参

现在回到开头的问题。类实例化了 `good1`、`good2` 一万个对象，每个对象都有自己的一份 `m_name`、`m_price`、`m_amount`（修改 `good1` 的价格不影响 `good2`）；但成员方法编译成指令后放在代码段，**全类只有一套**。

那么 `good1.show()` 执行时，`show` 怎么知道该读 `good1` 的成员变量而不是 `good2` 的？

答案说出来平平无奇：**调用时把对象的地址当实参传了进去**。`good1.init("面包", 20.5, 100)` 在底层等效于：

```cpp
init(&good1, "面包", 20.5, 100);
```

汇编层从来只有函数调用，没有"面向对象的汇编"。编译器在编译成员方法时，给**每个成员方法的参数表开头悄悄加了一个形参**——`this` 指针，类型是 `CGoods*`，专门用来接收调用者的地址：

```cpp
// 编译器眼中的 init（你写的版本会被自动改写成这样）
void init(CGoods* this, const char* name, double price, int amount)
{
    strcpy(this->m_name, name);
    this->m_price = price;
    this->m_amount = amount;
}
```

方法体里每一次访问成员变量，编译器都改写成 `this->xxx`。你写 `m_price = price`，它编译成 `this->m_price = price`——你不写 `this`，编译器替你写；你写了，它就不再重复加。

所以"一套方法伺候一万个对象"的机制完整了：谁调用，谁的地址就通过 `this` 进来，方法里所有成员访问都顺着 `this` 落到那个对象的内存上。`good1.show()` 时 `this == &good1`，读的是面包；换成 `good2.show()`，同一个函数，`this == &good2`，读的是空调。

这也解释了两条日常规则。成员方法必须用对象调用——不指定对象，`this` 就没有实参来源；静态成员函数没有 `this`——它不需要区分对象，这是成员方法篇的内容。

## 小结

- OOP 出发点：找实体 → 拆属性与行为（ADT）→ 属性写成成员变量、行为写成成员方法
- 类是抽象类型不占内存，对象是实体、在栈上占内存；一个类型可以实例化无数对象
- 封装：属性私有 + 公有 get/set；返回私有数据一律 `const`，防指针泄露
- 类内定义自动内联；类外定义加 `CGoods::`，且加在方法名前
- 对象大小只由成员变量决定，按最大成员对齐、补位；`cl /d1reportSingleClassLayout` 可查布局
- 每个对象有独立的成员变量，成员方法全类一份；编译器给每个成员方法加隐含形参 `this` 接收调用者地址，成员访问实际都是 `this->成员`

`this` 解决了"方法怎么找到对象"。但对象**出生时**呢？`good1` 的三个成员变量现在是随机值，谁来初始化它们？对象消亡时谁做清理？下一篇：构造函数与析构函数。
