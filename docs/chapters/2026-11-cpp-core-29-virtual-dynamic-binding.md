# 虚函数与动态绑定：pb->show() 为什么调到了 Derived

![vfptr 与虚函数表：对象头部的指针、运行期加载的表、动态绑定的三条指令](/assets/images/cpp-core/cpp-core-29-virtual-dynamic-binding.png)

上一篇留下违和感：`Base* pb = &d; pb->show();`——`pb` 明明指向 Derived 对象，调用的却是 Base 的 `show()`。给 `show()` 加一个 `virtual` 关键字，同一行代码立刻改调 Derived 的版本。

一个关键字改变函数调用去向，背后是 C++ 运行时体系里最大的一块机器：**虚函数表**。这篇把"加 virtual 之后编译器和运行时各做了什么"拆成四件事，再用三条汇编指令看清"动态绑定"这个词的物理含义——它不是形容词，是真实的运行时查表过程。

边界：单继承下的虚表布局；多继承（多个 vfptr）、虚继承（vbptr）在菱形继承篇展开；虚析构函数在笔试题篇。

## 1. 先看没有 virtual 的世界：静态绑定

"绑定"这个词的准确含义是**函数调用的确定**：一次 `pb->show()` 到底执行哪段代码，谁说了算、什么时候说了算。

没有 virtual 时，答案在编译期就定死了。看 `pb->show()` 的反汇编：

```asm
call Base::show()        ; 直接 call 具体函数地址
```

编译器查 `pb` 的静态类型（`Base*`），到 Base 作用域找到 `show`，把它的地址直接写进指令。**编译期确定调用 = 静态绑定**。普通函数、前面所有篇章里的一切函数调用，全部是静态绑定——这也是"指针的静态类型决定能力"（第 28 篇）的底层样子：指令里写死了函数地址，运行时没有任何腾挪空间。

顺带用 `typeid` 验证一下这个世界的规则：`sizeof(Base)` 是 4（只有 ma），`sizeof(Derived)` 是 8，`typeid(pb).name()` 打出 `Base *`（变量类型永远静态），`typeid(*pb).name()` 打出 `class Base`——**没有虚函数时，`*pb` 识别的是编译期能看出来的类型**（静态类型），运行时毫无参与。

## 2. 加上 virtual：编译器与运行时各干四件事

给 Base 的两个 `show` 都加上 `virtual`，整个类型系统发生四个变化，逐条记牢：

**其一：编译期给"类型"生成一张虚函数表（vf table）。**一个类型一张，唯一。表里放三样东西：**RTTI 指针**（指向类型信息，简化理解成类型字符串——这张表是谁生成的就指向谁，Base 的表指向 Base）；一个**偏移量**（多数情况为 0，含义在虚继承篇揭晓）；**各个虚函数的地址**，按声明顺序排列。运行时这张表加载进 **.rodata 只读数据区**——和常量字符串住同一片，只许读不许写，你敢通过指针偏移摸到它并写入，程序直接报错。

**其二：该类的每个对象，内存头部多 4 字节 vfptr。**`Base` 对象从 4 字节变 8 字节：前 4 字节是 `ma`，**最前面**是 vfptr，指向本类型的虚函数表。同一个类型的 N 个对象，vfptr 全部指向同一张表。两个推论常考：**虚函数的个数不影响对象大小**（对象里只多那一个指针），**影响的是虚函数表的大小**（多一个虚函数，表里多一项）。

**其三：派生类"连坐"。**Derived 没写 virtual，但它从 Base 继承了两个虚函数，于是 Derived 类型也有一张自己的虚函数表，Derived 对象也多一个 vfptr——`sizeof(Derived)` 变成 12。

**其四：覆盖发生在虚函数表里。**Derived 的 `show()` 与 Base 的 `show()` 返回值、函数名、参数列表全部相同，且基类版本是虚函数——**派生类版本自动成为虚函数**，两者构成**覆盖**（override，也叫重写）关系。编译器生成 Derived 的虚函数表时，把"从 Base 继承来的 `show()` 地址"那一项**替换成 Derived 版本的地址**。

这就是三分法的最后一分落定：覆盖的本质是**虚函数表中地址的覆盖**。Derived 没有重写 `show(int)`，所以它表里那一项还是 Base 的地址。

## 3. 动态绑定的三条指令

现在再看 `pb->show()` 的反汇编——它不再是 `call Base::show()`，而是三条指令：

```asm
mov  eax, dword ptr [pb]     ; ① 取 pb 所指对象的前 4 字节 → vfptr
mov  ecx, dword ptr [eax]    ; ② vfptr 指向虚函数表，取出第一项 → show 的地址
call ecx                     ; ③ 调用寄存器里的地址
```

对着这三条指令，"动态"二字落到实处：编译器生成的指令里**没有写死任何函数地址**——call 的是一个寄存器。寄存器里最终是什么地址，取决于第①步取到的 vfptr 指向哪张表：`pb` 若指向 Base 对象，取到 Base 表、调 Base 版；指向 Derived 对象，取到 Derived 表、调覆盖后的 Derived 版。**只有运行到这条指令时才知道调用谁——这就是动态绑定**：运行期确定的函数调用。

所以两条规则可以对仗着背：**静态绑定绑普通函数，指令直接 call 地址；动态绑定绑虚函数，指令 call 寄存器**。也回答了上一篇的违和感：`pb` 指向 Derived 对象 → 对象头部是 Derived 的 vfptr → 查到 Derived 的表 → 取到覆盖后的地址——一切顺理成章。

顺带把 `typeid(*pb)` 的变化收进同一个体系：基类有虚函数后，`*pb` 识别的是**运行期类型**——顺着对象头部的 vfptr 找到实际那张表（Derived 的），取表头的 RTTI，打印 `class Derived`。typeid 的行为差异（无虚函数看静态类型 / 有虚函数看动态类型）正是"虚函数表里存 RTTI"的直接应用。

## 4. 几个细则

**vfptr 的位置是偏移量 0。**虚函数指针在对象内存的最前面——表里那个"偏移量"字段记录的就是它，多数情况下为 0（虚继承场景例外，后续篇章）。这也解释了第①条指令为什么取"对象前 4 字节"。

**表内顺序与声明顺序一致。**先声明的虚函数在前。Derived 的表里：重写的 `show()` 在自己的位置换地址，未覆盖的 `show(int)` 保留 Base 的地址——按继承顺序排列。

**验证工具还是那个。**第 10 篇的 `cl /d1reportSingleClassLayoutDerived 文件.cpp` 会把整个布局打印出来：vfptr、RTTI 指针、偏移量、虚函数地址的排布一览无余。对虚表存疑时，别猜，跑命令。

**动态绑定的触发条件要记全。**必须同时满足：指针或引用调用 + 调用的是虚函数。写成对象调用（`d.show()`）没有动态绑定——对象类型在编译期确定，没有"可能指向别人"的问题，直接静态绑定。多态发生的前提是**用基类的指针或引用持有派生对象**（第 28 篇的上转）。

## 小结

- 绑定 = 函数调用的确定。静态绑定：编译期 call 具体地址，普通函数全是；动态绑定：运行期查表 call 寄存器，只有虚函数
- 加 virtual 的四个变化：类型生成唯一虚函数表（RTTI 指针 + 偏移量 + 虚函数地址，运行时在 .rodata 只读区）；对象头部多 4 字节 vfptr；派生类连坐（也有表有 vfptr）；派生类重写同名同参虚函数 → 自动成为虚函数 → 表中地址被覆盖
- 虚函数个数不影响对象大小（只多一个 vfptr），影响虚函数表大小
- 覆盖 = 虚函数表中地址的覆盖；未重写的虚函数在派生类表里保留基类地址
- 动态绑定三条指令：取对象头部 vfptr → 查表取地址 → call 寄存器；编译期不知道调谁，运行期才知道
- 基类有虚函数后，`typeid(*pb)` 识别运行期类型；无虚函数时识别编译期类型
- 动态绑定触发条件：指针/引用调用 + 虚函数，缺一不可

查表机制齐了，但它只是引擎。下一篇把场景拼完整：一个循环、一个基类指针数组、一堆不同的派生对象——**多态**到底是什么，以及为什么说它是面向对象最强大的机制。
