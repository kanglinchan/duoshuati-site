# malloc 与 free：堆上的内存由你全权负责

上一课我们把内存分了四个片区，其中栈是"自动管理"的模范生——函数一来就有，函数一走就没。但栈有个死穴：**大小必须在编译期定死，而且函数一返回就没了。**

如果数据量要到运行时才知道呢？比如让用户随便输入一篇文章，字数不固定；比如做一个通讯录，联系人数量不固定。栈帮不了你，这时候就要请出**堆（heap）**——一块"要多少给多少、什么时候还你说了算"的自由内存区。

管理堆的工具就两个函数：`malloc` 负责申请，`free` 负责归还。这一课把它们用透，顺便看清背后发生了什么。

### 1. malloc：要多少，给多少

`malloc` 的用法一句话说完：

```c
#include <stdlib.h>

int *p = malloc(sizeof(int) * 100);   /* 申请 100 个 int 的空间 */
if (p == NULL) {
    /* 申请失败（内存耗尽），得处理 */
}
/* ……随便用，p[i]、*(p+i) 都行…… */
free(p);      /* 用完了，归还 */
p = NULL;     /* 好习惯：释放后立刻置空 */
```

拆解一下这个流程：

- `malloc(sizeof(int) * 100)`：告诉它要多少**字节**（400），它返回这块内存的首地址。返回值类型是 `void*`（通用指针），赋给 `int*` 时自动转换，不用强制转型。
- **必须检查返回值**：申请失败会返回 NULL。直接拿来用，第一次解引用就崩。
- **必须 free**：申请到的内存从 malloc 那一刻起就归你管，直到你 free 它。**你不 free，它就一直在那占着**——这就是内存泄漏。

和栈对比一下差别：

```c
void foo(void) {
    int a[100];                  /* 栈：函数返回就回收 */
    int *b = malloc(100 * sizeof(int));  /* 堆：函数返回后还在！ */
}
/* 函数结束后：a 没了；b 指向的内存还在，等你 free */
```

堆内存的生命周期由你掌控，这正是它存在的意义。

### 2. malloc 不是魔法：批发零售的生意

很多人以为 `malloc` 是直接向操作系统要内存的系统调用。其实不是——**malloc 是个标准库函数，一个"二道贩子"。**

它先从操作系统那里**批发**一大块内存（一次要很多，走系统调用），然后在自己的小仓库里切成一小块一小块**零售**给你的程序。你每次 `malloc(100)`，它就在仓库里找一块够大的空地给你。

它怎么管这个仓库？最简单的模型是这样的：

```text
仓库内存：[管理头| 你的数据 ][管理头| 空闲   ][管理头| 你的数据 ]…
            ↑每块前面藏着一个小账本：多大、是否空闲
```

- 每块内存前面有个**管理区域**，记录着"我多大、是空闲还是用掉了"。
- `malloc` 顺着管理区域找一块够大的空闲块，切给你，把标记改成"使用中"。
- `free` 把标记改回"空闲"，如果相邻两块都空闲，就合并成一大块（防止碎成渣）。

知道这些有什么用？用处大了——它解释了一个经典诡案：

**为什么内存越界写，崩溃的却往往是下一次 malloc/free？**

因为你写超了，踩烂的是紧邻的**管理区域**——那块小账本。程序当时一点事没有，直到下次 malloc/free 来查账，发现账目错乱，直接崩溃。崩溃现场离案发现场十万八千里，这就是内存 bug 难查的根源。

### 3. free 之后：最阴险的 bug 登场

看一段代码：

```c
int *p = malloc(sizeof(int) * 10);
p[0] = 42;
free(p);
printf("%d\n", p[0]);   /* 居然打印出 42？！ */
```

free 都 free 了，怎么还能读到 42？

因为 **free 只是在那块内存的管理区域上盖了个"空闲"的章，并不会清空里面的数据。** 数据还赖在那，直到下次 malloc 把这块地分给别人、新主人写入新数据为止。

于是诞生了 C 语言最阴险的 bug 类型——**use-after-free（释放后使用）**：

```text
p ──┐
    ├─→ 同一块内存
q ──┘        你从 p 这条路 free 了它，q 却还指着它
             q 暂时还能读到旧数据（因为没被覆盖）
             → 某天别处 malloc 占用了这块地，q 的数据突然被改
```

程序在千里之外的地方莫名其妙地出错，而根源是早就执行过的那次 free。这种 bug 从埋雷到爆炸隔着漫长的时空，极难定位。

防御手段：

- **free 后立刻 `p = NULL`**。再误用就是解引用空指针，当场段错误——立刻暴露，比静默出错强一百倍。
- 大型项目用工具兜底：**Valgrind** 能精确报出 use-after-free、内存泄漏、越界读写，Linux 下调试内存问题必备。

### 4. 碎片化：堆的慢性病

反复申请、释放不同大小的内存，堆会发生什么？

```text
[使用中][空20][使用中][空8][使用中][空100]…
```

空闲块东一块西一块，加起来可能有好几百字节空闲，但你想申请一块 200 字节的连续内存——**没有一块够大，申请失败**。这就是**碎片化（fragmentation）**：总量够，但都是碎的，用不了。

C 没有垃圾回收，也不会帮你把内存块挪来搬去整理（指针直接暴露了地址，内存不能随便搬家，否则你的指针全失效）。所以碎片化只能缓解，不能根治：

- **能一次申请大块，就别频繁申请小块**。
- 需要反复扩容的动态数组，**按倍数扩**（比如每次翻倍），而不是加一个元素扩一次。JS 的数组、`ArrayList` 内部都是这个策略。
- 超大量的离散数据，考虑用链表这类不要求连续内存的结构（第 8 课）。

### 5. calloc 和 realloc：malloc 的两个兄弟

堆操作还有俩常用函数，一并说了。

**`calloc` = malloc + 清零。**

```c
int *p = calloc(100, sizeof(int));   /* 申请 100 个 int，并全部置 0 */
/* 等价于 malloc(100 * sizeof(int)) 然后 memset 清零 */
```

**realloc = 调整已分配内存的大小。** 数组不够用了，不用重新 malloc + 拷贝 + free，一句话搞定：

```c
p = realloc(p, sizeof(int) * 200);   /* 从 100 个扩到 200 个，数据保留 */
```

但 realloc 有个坑，千万小心：**它可能把数据搬到新地址去**。如果原位置后面没有足够的连续空闲空间，realloc 会在别处找一块更大的，把数据拷过去，然后返回**新地址**。

所以下面这种写法是错的：

```c
/* 危险示范 */
int *q = p;
realloc(p, new_size);   /* 如果 p 被搬到了新地址，q 就指向了旧（已释放）地址 */
```

正确姿势是接住 realloc 的返回值（那才是真正的地址），而且要防着它失败返回 NULL：

```c
int *tmp = realloc(p, new_size);
if (tmp == NULL) {
    /* 扩容失败，p 指向的旧内存还在，还能用 */
} else {
    p = tmp;    /* 换新地址 */
}
```

### 6. 两个细节：对齐与字节序

最后补两个和内存打交道时绕不开的底层概念。

**对齐（alignment）**：CPU 读内存有"讲究"——4 字节的 int 最好放在 4 的倍数地址上，8 字节的 double 放在 8 的倍数地址上，否则要么变慢、要么有的 CPU 直接罢工。所以结构体里成员之间常被编译器偷偷塞入**填充（padding）**：

```c
struct {
    char c;      /* 1 字节，但后面要放 int，所以补 3 字节填充 */
    int  i;      /* 4 字节 */
} s;
sizeof(s);       /* 8，不是 5 */
```

![结构体的对齐与填充：sizeof 往往比成员之和更大](/assets/images/c-pointers/cptr-04-struct-padding.png)

这解释了为什么结构体的大小常常比成员加起来大。malloc 返回的地址一定是按最严格类型对齐好的，你不用操心；但用 `sizeof` 算结构体大小、手动排布内存时，得把填充算进去。

**字节序（endianness）**：一个 4 字节的 int `0x12345678`，在内存里到底是按 `12 34 56 78` 存，还是按 `78 56 34 12` 存？答案是：**看 CPU。** x86 用小端（little-endian，低位在前），网络协议用大端（big-endian，高位在前）。

```c
int x = 0x12345678;
unsigned char *p = (unsigned char*)&x;
printf("%02x %02x %02x %02x\n", p[0], p[1], p[2], p[3]);
/* x86 输出：78 56 34 12（小端） */
```

什么时候要关心它？**把内存里的原始字节直接写文件、发网络时。** 同一台机器上读写没问题；跨机器交换数据时，字节序不同就会读出错乱的数据——这是网络编程和二进制文件格式的经典坑。

### 小结

- `malloc` 申请、`free` 释放；返回值要检查，释放后立刻置 NULL
- malloc 是内存"二道贩子"，越界写会踩坏它的账本，崩溃总在千里之外
- free 只是盖"空闲"章，数据还在——use-after-free 由此而生，用 Valgrind 抓
- 碎片化：总量够但连不成整，只能缓解（大块申请、翻倍扩容）
- `realloc` 可能搬地址，必须接住返回值，且先存临时变量再判 NULL
- 结构体有填充，sizeof 比想象大；跨机器传二进制数据要小心字节序
