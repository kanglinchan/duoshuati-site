# 继承多态笔试题实战：四道名题拆解

![四道名题：交换 vfptr、默认值取自静态类型、private 方法被多态调到、memset 清 vfptr](/assets/images/cpp-core/cpp-core-41-polymorphism-quiz.png)

前面 12 篇把继承多态的原理拆到了指令级。原理是弹药，这一篇是靶场：四道大厂校招笔试真题，每一道都把"编译期做什么、运行期做什么"这条主线拷问一遍。

答题心法先给出来，四道题全靠它：**拿到代码先分拣——哪些事编译期定（访问权限、默认值压参、静态绑定），哪些事运行期定（动态绑定查表、虚函数实际指向）。**分拣清楚，答案往往自己浮出来。

边界：四道题以 32 位 MSVC 为准（vfptr 占对象头 4 字节）；题目原型来自腾讯等大厂校招笔试。

## 1. 题一：交换两个对象的 vfptr

例. Animal 抽象基类（纯虚 `bark`）+ Cat、Dog 各自重写。基类指针各指一个对象，然后来一段熟悉的内存交换：

```cpp
Animal* p1 = new Cat("加菲");
Animal* p2 = new Dog("二哈");

int* pint1 = (int*)p1;      // 指向 Cat 对象的头部
int* pint2 = (int*)p2;      // 指向 Dog 对象的头部
int tmp = *pint1;
*pint1 = *pint2;            // 交换两个对象的"前 4 字节"
*pint2 = tmp;

p1->bark();     // 输出？
p2->bark();     // 输出？
```

解. 对象的"前 4 字节"是什么？**vfptr**（第 29 篇：有虚函数的对象头部多 4 字节虚函数指针）。这段交换代码换的不是名字、不是数据，是**两个对象的虚函数表指针**。

交换之后：Cat 对象头部躺着 Dog 的 vfptr，Dog 对象头部躺着 Cat 的 vfptr。于是 `p1->bark()` 走动态绑定——取 p1 所指对象（Cat）头部的 vfptr → 拿到的是 **Dog 的虚函数表** → 取出 Dog 重写的 bark → **加菲，汪汪**。同理 `p2->bark()` 输出**二哈，喵喵**。

名字和叫声彻底错位，因为动态绑定只认"对象头部指向哪张表"，不认"这对象声明是谁"。这道题的考点浓缩成一句：**多态调用的真相是查对象头部的表，表指错了，行为就错位**。能秒懂这题，说明第 29 篇的三条指令真的进脑子了。

## 2. 题二：动态绑定调了派生类方法，默认值却是基类的

例. Base 有虚函数 `show(int i = 10)`，Derived 覆盖它且**把默认值改成 20**。基类指针指向派生对象，无参调用：

```cpp
class Base
{
public:
    virtual void show(int i = 10) { cout << "Base::show i=" << i; }
};
class Derived : public Base
{
public:
    void show(int i = 20) { cout << "Derived::show i=" << i; }   // 覆盖，默认值不同
};

Base* p = new Derived();
p->show();          // 输出？
```

解. 调用的是 **Derived::show**（动态绑定，查 Derived 表——这半题人人会答）。但打印的是 **i = 10**——**默认值用了基类的**。派生类的默认值 20 彻底没用武之地。

为什么？把一次调用的两个阶段分开看：

- **压参数发生在编译期**。`p->show()` 无实参，编译器给形参压默认值——可编译期 `p` 只是 `Base*`，它**只能看见 Base 作用域里的 show**，于是按 Base 的默认值生成 `push 0Ah`（10 入栈）。参数压栈的指令此时已经写死。
- **函数地址发生在运行期**。动态绑定三条指令跑完，从 Derived 表里取出派生类函数地址，call 过去——但参数早在编译期压好了，派生类那边的默认值 20 根本没有出场机会。

结论直接可用：**继承结构中，给基类与派生类的同名覆盖方法配不同的默认值毫无意义**——多态调用下派生类的默认值永远用不到。要么不设默认值，要么两处默认值保持一致。

## 3. 题三：private 的方法被多态调到了

例. 同样的继承结构，Derived::show 改成 **private**。基类指针指向派生对象再调用：

```cpp
Base* p = new Derived();
p->show();          // Derived::show 是 private —— 能调到吗？
```

解. 能调到，输出派生类版本。又一次"编译期 vs 运行期"的分离：

- **访问权限检查在编译期**。编译器检查"`p->show()` 这个调用合不合法"时，看的同样是 **p 的静态类型 Base**——Base::show 是 public，放行。派生类的 private 它根本没看。
- **实际调到谁在运行期**。动态绑定查 Derived 表，取出的地址就是那个 private 的 Derived::show——运行期的内存没有权限概念，指令该跳就跳。

反向变体更有意思：Base::show 设为 **private**、Derived::show 设为 public，同一行代码**编译错误**——"无法访问 private 成员"，检查的又是 Base 那份。哪怕你推理出"运行时调的是派生类的 public 版本"，编译都过不去，哪来的运行。

一句话总结这题：**权限看静态类型（编译期），执行看动态类型（运行期）**。访问限定符是编译期的语法关卡，不是运行时的保安。

## 4. 题四：memset 清掉 vfptr 之后

例. 基类构造函数里有一段"清零"代码：

```cpp
class Base
{
public:
    Base()
    {
        clear();
        cout << "call Base ctor" << endl;
    }
    void clear() { memset(this, 0, sizeof(*this)); }   // 把整个对象清成 0
    virtual void show() { cout << "call Base::show" << endl; }
};
```

两段测试代码，判断各自的运行结果：

```cpp
// 代码 A
Base* pb = new Base();
pb->show();               // ？

// 代码 B
Base* pd = new Derived(); // Derived 覆盖了 show，无自定义构造
pd->show();               // ？
```

解. **代码 A 崩溃，代码 B 正常输出派生类版本。**这道题考的是全书最隐秘的一个知识点：**vfptr 的写入时机**。

先看 A 为什么崩。构造函数执行 clear，把 Base 对象的全部内存清 0——包括**头部的 vfptr**。随后 `pb->show()` 走动态绑定：取对象头 4 字节 → 是 0 → 从地址 0 读虚函数表——**零地址（NULL 页）不可读**，段错误崩溃。注意第 30 篇的结论在这里呼应：构造函数中调虚函数是静态绑定，但这里是**构造完之后**经指针调用，走的是动态绑定，所以才会去读那个已被清零的 vfptr。

再看 B 为什么没事——关键在 vfptr 的写入时机。每个类的构造函数在被调用时，指令序列是：

```text
① push ebp / 建帧 / 栈初始化（第 01 篇的进门三件套）
② 把本类型虚函数表的地址写入对象的 vfptr   ← 隐含动作，编译器插入
③ 执行你在函数体里写的代码                  ← clear 在这里才跑
```

new Derived 的构造链：Base 构造 → ②写入 Base 表地址 → ③clear 把 vfptr 清零（对象此刻"表指针失效"）→ Derived 构造 → **②再写入 Derived 表地址**——派生类构造函数开头的那次写入，把被清零的 vfptr **修复**了。之后 show() 查到的是有效的 Derived 表，一切正常。

所以完整结论是：**vfptr 在每层构造函数中、栈帧就绪后、用户代码前被写入本类型的虚函数表地址**。构造函数清零对象是自残行为（A 题），但只要派生层构造会再走一遍②，指针就被救回来（B 题）。memset(this, 0, ...) 这种写法在含虚函数的类里是禁区——它连对象"我是谁"的凭证都擦了。

## 5. 四题一线

把四道题的底层要点收进一张表：

| 题 | 考点 | 一句话结论 |
|---|---|---|
| 交换 vfptr | 动态绑定只认对象头部 | 表指错了，行为就错位 |
| 默认值错位 | 压参在编译期、查表在运行期 | 派生类的默认值在多态下永远用不到 |
| private 被调 | 权限查静态类型、执行看动态类型 | 访问限定符是编译期关卡 |
| memset 清零 | vfptr 在每层构造开头写入 | 含虚函数的类禁 memset(this)；派生层构造能"救回"vfptr |

四道题共用一个母题：**编译期与运行期的分工**。静态类型管编译期的一切检查（权限、默认值、能否调用），动态类型管运行期的实际执行（查哪张表、调哪个版本）。分析继承多态的任何问题时，先做这道分拣题，八九不离十。

## 小结

- 交换 vfptr 题的行为错位证明：多态调用的本质是"查对象头部的虚函数表"
- 默认值题：参数压栈在编译期按**静态类型**的默认值完成；动态绑定只决定函数地址——派生类默认值在多态调用下永远无效，覆盖方法的默认值应与基类一致或干脆不设
- 权限题：访问权限在编译期按静态类型检查，运行期无权限概念——private 的方法可以被基类指针"合法"调到；反向则编译不过
- memset 题暴露 vfptr 写入时机：每层构造函数中（栈帧就绪后、用户代码前）写入本类型虚表地址；清零 vfptr 后经指针调虚函数必崩（读零地址），派生类构造的再写入是"救命"机制
- 母题：静态类型管编译期（权限/默认值/合法性），动态类型管运行期（查表/执行）——先分拣再分析
