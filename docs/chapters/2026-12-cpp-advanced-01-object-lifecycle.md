# 对象背后调用了哪些函数：4 行代码，11 次调用

![对象生命周期全景：初始化 vs 赋值、显式/隐式临时对象、指针与 const 引用绑临时对象、11 次调用](/assets/images/cpp-advanced/cpp-advanced-01-object-lifecycle.png)

总有人说"C++ 比 C 慢"。这句话的前半句是对的，后半句错得离谱——**C 和 C++ 都是本地编译型语言，语言本身的效率没有差别**；慢的是不了解对象背后发生了什么的开发者：你以为在写一行赋值，编译器在背后调了构造、拷贝构造、析构三趟。

"对象优化"这个系列就干一件事：看清每个对象操作背后调用的函数，然后把不必要的调用省掉。本篇是第一块地基——给 Test 类的四个经典函数（构造/析构/拷贝构造/赋值）全部加上打印，逐行审讯每一条对象语句。

边界：本文对象不占外部资源（浅拷贝安全，聚焦"调用了什么"）；"怎么省掉这些调用"是后续几篇的主题；编译器优化以 MSVC/GCC 通用的"临时对象拷贝构造新对象"场景为准。

## 1. 窥探工具：四件套加打印

```cpp
class Test
{
public:
    Test(int a = 5) : ma(a) { cout << "构造"; }
    Test(const Test& t) : ma(t.ma) { cout << "拷贝构造"; }
    Test& operator=(const Test& t) { ma = t.ma; cout << "赋值"; return *this; }
    ~Test() { cout << "析构"; }
private:
    int ma;
};
```

带默认值的构造函数一函数三用（第 08 篇）：全默认 / 传一个 / 传两个。拷贝构造与赋值里的"拷贝数据"这个对象用不上，写出来只为口径完整。接下来每条语句都靠打印定案。

## 2. 初始化与赋值的分界线

```cpp
Test t1(10);        // 构造
Test t2(t1);        // 拷贝构造
Test t3 = t1;       // 拷贝构造！不是赋值
t2 = t3;            // 赋值
```

第三行的 `=` 是天字第一号陷阱。判据在第 16 篇立过、这里正式立为铁律：

> **左边对象正在定义 → 初始化（调拷贝构造）；左边对象已存在 → 赋值（调 operator=）。**

`t3 = t1` 里 `t3` 正在诞生，所以是"用 t1 拷贝构造 t3"——写法带等号但语义是构造。对内置类型，初始化和赋值生成的指令一模一样，混着说不碍事；对对象，两者调用完全不同的函数，混着说就答错题。

## 3. 临时对象：显式与隐式

**显式生成**：`Test t4 = Test(20);`

直觉分析是三步：构造临时对象 → 用它拷贝构造 t4 → 语句结束析构临时对象。上机打印只有一次"构造"——**临时对象根本没产生**。

这条优化是全平台 C++ 编译器的共同行为，值得作为规则背下：

> **用临时对象拷贝构造新对象时，临时对象不产生，直接按构造参数构造新对象。**

道理顺推即通：这句代码的最终目的只有一个——把 t4 造出来。为造 t4 而先造一个临时对象、拷贝一遍、再析构，全是无效功。编译器直接跳过中间人，按 `20` 这个参数一步构造 t4。

**赋值右边临时对象必须生成**：`t4 = Test(30);`

这次临时对象逃不掉了——t4 已存在，赋值需要"拿来一个东西"填给形参引用，没有对象就没得赋。打印是三拍：构造（临时对象）→ 赋值 → 析构（临时对象）。对比第 3 节的两行，同一个 `Test(30)`，命运由左边对象"是否存在"决定。

**隐式生成**：`t4 = 30;`

等号右边连 `Test` 类型都没出现，直接一个整数。编译器的处理：要把 int 转成 Test，就找**带 int 参数的构造函数**——找到了（就是那个默认值构造），隐式生成临时对象再赋值。打印与显式版完全相同：构造 → 赋值 → 析构。第 25 篇"单参构造承担隐式转换"的机制在这里原样重演。

## 4. 谁能安全地绑定临时对象

```cpp
Test* p = &Test(10);          // 危险
const Test& r = Test(20);     // 安全
```

指针版：临时对象出语句即析构（没名字，语句之外无处引用它），`p` 从此指向一块已析构的内存——野指针，后面每次解引用都是事故。

引用版：引用的语义是"给内存起别名"（第 07 篇）——给临时对象起了名字 `r`，它的生命周期**延长到引用变量的生命周期**：函数 return 时才随 `r` 一起析构。C++ 标准专门为"const 引用绑定临时对象"规定了这条生命周期延长规则。

所以结论是成对的：**指针指临时对象不安全；const 引用绑临时对象安全**。注意普通引用 `Test& r = Test(20);` 在新编译器下直接编译报错（第 07 篇讲过：非常量左值引用绑不了右值）——必须 const。

## 5. 不同存储位置的对象生灭

把全局、静态局部、堆、栈四类对象摆进一个 main，析构打印给出完整时序：

- **全局对象**（数据段）：`main` 之前构造，`main` 结束后析构——活得最久；
- **静态局部对象**：数据段内存程序启动就分配好，但**构造发生在第一次执行到它那行**；程序结束时析构；
- **堆对象**（`new Test(70)`）：出语句**不析构**——它不是临时对象，只有 `delete` 才触发析构 + free（第 11 篇的两步）；
- **`new Test[2]`**：数组无法逐个指定初始化方式，两个元素都走默认构造；`delete[]` 时析构两次再释放整块；
- **栈对象**：出作用域按构造的逆序析构。

析构打印的完整序列里有个细节值得停一秒：静态局部对象 T4 构造得晚（第一次执行到才构造），但析构排在数据段对象的逆序里——"先构造的后析构"的老规则（第 11 篇）跨存储位置照样成立。

## 6. 函数调用：实参到形参是初始化

```cpp
Test getObject(Test t)          // 形参：拷贝构造
{
    Test tmp(t.getData());      // 构造
    return tmp;                 // 拷贝构造 main 栈帧上的临时对象
}                               // 析构 tmp、析构形参 t

Test t2;                        // 构造 t2
t2 = getObject(t1);             // 赋值 + 析构临时对象
```

每一步都有名堂。**实参 t1 传给形参 t 是初始化不是赋值**——形参 t 正在定义，调拷贝构造（内置类型两者无差别，对象必须分清，这就是第 2 节铁律的第三次出场）。**返回值带不出来**：`tmp` 是局部对象出不了函数，又不能返回它的指针或引用（第 16 篇的老规则），所以 return 处在 **main 的栈帧上拷贝构造一个临时对象**来中转。函数结束时按逆序析构 `tmp` 和形参 `t`。回到 main，临时对象给 `t2` **赋值**（t2 已存在），然后临时对象出语句析构。

数一数总账：构造 t1、构造 t2、拷贝构造形参、构造 tmp、拷贝构造临时对象、析构 tmp、析构形参、赋值、析构临时对象、析构 t2、析构 t1——

**四五行代码，背后 11 次函数调用。**

这 11 次里有几次是白干的？形参的拷贝构造+析构（2 次）、tmp 的拷贝构造+析构链条（相关 2 次）、临时对象的拷贝构造+析构（2 次）……优化空间大得惊人。怎么省，正是接下来三篇的内容：移动语义省掉临时对象的深拷贝（02、03 篇），三条规则从写法层面直接砍掉整段调用（04 篇——剧透：11 次能优化到 4 次）。

## 小结

- 初始化 vs 赋值的铁律：左边正在定义 → 拷贝构造；左边已存在 → operator=。`Test t3 = t1;` 是拷贝构造
- 用临时对象拷贝构造新对象：临时对象被全平台编译器优化掉，直接构造新对象；赋值右边的临时对象必须生成（赋值需要实物）
- 隐式临时对象：整数赋给对象时按单参构造隐式生成，与显式 `Test(30)` 行为完全相同
- 指针指临时对象 = 野指针（出语句析构）；const 引用绑临时对象安全（生命周期延长到引用的作用域）；普通引用绑右值直接编译错
- 全局对象 main 前构造；静态局部对象首次执行到才构造；堆对象只有 delete 才析构；先构造的后析构跨存储位置成立
- 实参传形参是初始化（拷贝构造）；返回局部对象在调用方栈帧生成临时对象中转——四行代码 11 次调用，优化空间巨大
