# 多态的本质：一个接口，千种形态

![多态：基类指针指向不同派生对象调用同名覆盖方法；动态绑定链路与开闭原则](/assets/images/cpp-core/cpp-core-30-polymorphism.png)

"请解释一下多态。"——OOP 面试的必答题，也是背诵重灾区。背出来的答案是"多种形态"，追问"多态解决了什么工程问题"就哑火。

这篇用一个动物园的接口设计案例把多态讲透：先看**不用多态**的写法烂在哪，再看多态的写法好在哪，最后把底层链路（上一篇的三条指令）接到业务层。顺带修正一个流传极广的误解——"虚函数的调用就是动态绑定"：**错**，这篇给你完整判定表。

边界：虚析构函数、哪些成员函数不能是虚函数，在笔试题篇集中处理；多态在设计模式中的应用属于进阶内容。

## 1. 静态多态：先给"多态"这个词划一半出去

多态字面义"多种形态"。**一个名字呈现出多种形态**这件事，编译期就有两处发生：

**函数重载**：一组 `compare` 同名不同参，调用点按实参匹配版本——一个名字、多种形态，编译期确定调谁（第 09 篇）。

**模板**：一套 `compare<T>` 代码，`int` 实例化一份、`double` 实例化一份——一份逻辑、多种类型形态，同样是编译期实例化（第 17 篇）。

这两样合称**静态多态**（编译期多态）。它们共享一个特征：**调用决策在编译期完成**，生成的指令里写死了地址。本篇的主角是另一半——**动态多态**（运行期多态），平时说"多态"默认指它。

## 2. 反例先行：三个重载接口的动物园

需求：Animal 基类，Cat、Dog、Pig 三个派生类各自会叫，对外提供让动物叫的 API。

不用多态的第一反应是写三个重载：

```cpp
class Animal {
protected:
    string name;
public:
    virtual void bark() {}       // 基类：所有动物都会叫，但"怎么叫"基类不知道
};
class Cat : public Animal {
public:
    Cat(string n) : Animal(n) {}     // 委托基类构造（第 27 篇）
    void bark() { /* 喵喵 */ }       // 重写
};
class Dog : public Animal { /* 汪汪 */ };
class Pig : public Animal { /* 哼哼 */ };

void bark(Cat& c) { c.bark(); }
void bark(Dog& d) { d.bark(); }
void bark(Pig& p) { p.bark(); }      // 三个接口，功能完全正确
```

功能正确的代码也可能是烂设计。这三个接口的问题在**变更时**爆发：新增一个 Sheep 类，就得加第四个 `bark(Sheep&)`；砍掉 Dog，就得删对应接口。**接口的数量被派生类的数量绑架**——API 与派生类紧耦合，改一处动一片。

软件设计的**开闭原则**说：对修改关闭，对扩展开放。需求变更（加动物、删动物）时，已有的接口一行不该动，只允许"新增代码"。三个重载的写法每加一类就改接口，直接违反。

## 3. 多态的定义与底层链路

三种动物全是 Animal 的派生类（第 28 篇的上转），那一个接口就够了：

```cpp
void bark(Animal* p)        // 一个接口吃所有动物
{
    p->bark();              // 调用的是……谁？
}

bark(&cat);     // 喵喵
bark(&dog);     // 汪汪
bark(&pig);     // 哼哼
```

同一行 `p->bark()`，三次调用三种叫声。这就是**动态多态的标准定义**：

> **继承结构中，基类指针（或引用）指向派生类对象，通过该指针调用同名覆盖方法——指向哪个派生类对象，就调用哪个派生类的覆盖方法。**

底层链路上一篇刚拆完，接到业务上走一遍：编译器看 `p` 的静态类型 Animal，`bark` 是虚函数 → 动态绑定，生成"取 vfptr → 查表 → call 寄存器"三条指令；运行时 `p` 指向 cat，就取 cat 对象头部的 vfptr → Cat 的虚函数表 → 重写的 Cat::bark；指向 dog 就走 Dog 的表。**指针指向谁，就顺着谁的对象头部找到谁的表**——三种叫声是查表查出来的。

至此继承的意义凑齐两条：**其一，代码复用**（第 26 篇：派生类白拿基类成员）；**其二，基类提供统一的虚函数接口，派生类各自重写，多态让"统一接口"与"千种实现"解耦**。第二条比第一条重要——它把接口与派生类数量脱钩，开闭原则落地：新增动物只需"继承 + 重写"，接口永远一个。

## 4. 修正误解：虚函数调用 ≠ 动态绑定

流传最广的误解在这里纠正。**虚函数的调用不一定发生动态绑定**，判定只看一件事：调用方式。把所有情况摆上桌：

| 调用方式 | 绑定方式 | 结果 |
|---|---|---|
| 对象调用：`b.show()` / `d.show()` | **静态绑定** | 各调各的版本 |
| 构造函数中调用虚函数 | **静态绑定** | 调当前正在构造的那个类的版本 |
| 基类指针/引用 → 基类对象 | 动态绑定 | 查 Base 表，调 Base 版 |
| 基类指针/引用 → 派生类对象 | 动态绑定 | 查 Derived 表，调覆盖版 —— **多态** |
| 派生类指针/引用 → 派生类对象 | 动态绑定 | 查 Derived 表 |

为什么对象调用是静态绑定？因为对象类型在编译期定死，动态绑定查到的表就是它自己类型的表，结果一样——没必要多绕三步指令，编译器直接 `call 地址`。构造函数里同理：正在构造的对象类型明确，虚函数按当前类版本静态调用（这也是"构造函数中调用虚函数不发生多态"的原理，笔试常考）。

最有意思的是最后一行变体：把派生类指针**强转**去指向基类对象（第 28 篇的下转，危险操作），它调虚函数**也是动态绑定**——查的是基类对象头部的表，也就是 Base 的表，调出来的是 Base 版本。指针/引用一律动态绑定，绑定结果跟着**实际指向的对象**走。

判定口诀收成一句：**看反汇编——call 具体地址是静态，call 寄存器是动态；而只有指针或引用调用虚函数，编译器才生成后者。**

## 小结

- 多态两分：静态多态 = 重载 + 模板（编译期定型）；动态多态 = 继承 + 虚函数 + 基类指针/引用（运行期查表）
- 动态多态定义：基类指针指向派生对象，调用同名覆盖方法——指向谁，调谁的版本
- 底层链路：指针指向谁 → 谁对象头部的 vfptr → 谁类型的虚函数表 → 谁重写的地址；三条指令接业务
- 多态的工程价值 = 开闭原则落地：`void bark(Animal*)` 一个接口吃所有派生类，新增/删除派生类不改接口；三个重载接口的写法被派生类数量绑架
- 继承的两点意义：代码复用；统一虚函数接口 + 多态解耦——第二条才是架构级的
- 虚函数调用不必然动态绑定：对象调用与构造函数中调用都是静态绑定；只有指针/引用调用才动态绑定，绑定结果跟着实际指向的对象走
- 口诀：call 地址是静态，call 寄存器是动态

多态让基类指针能"说人话"了，但如果基类的 `bark()` 根本不该有实现呢——"动物怎么叫"这个问题问 Animal 本身就是错的。下一篇：抽象类，把"只能被继承、不能被实例化"设计成语言规则。
