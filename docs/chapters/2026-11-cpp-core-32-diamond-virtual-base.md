# 菱形继承与虚基类：同一份数据，为什么搬进对象两遍

![菱形继承的重复数据与虚继承的解法：vbptr/vbtable、虚基类数据搬到对象末尾、D 亲自初始化](/assets/images/cpp-core/cpp-core-32-diamond-virtual-base.png)

C++ 允许多继承——一个派生类同时继承多个基类。好处直白：一次复用多个基类的代码。但它埋着本系列最绕的一个坑：**菱形继承**。D 继承 B 和 C，B、C 又都继承 A——D 的对象里躺着**两份** A 的数据：两个"姓名"、两个"身份证号"。

解药叫**虚继承**，配套出现本系列最后两个没讲过的运行时结构：**虚基类指针（vbptr）与虚基类表（vbtable）**。这篇把菱形的病根、虚继承的手术过程、以及一个著名的编译器差异坑一次讲完。

边界：多继承下多个 vfptr 的排布细节不展开（单继承的 vfptr 规则第 29 篇已够用）；文中内存布局以 32 位 MSVC 为准。

## 1. 菱形继承长什么样，病在哪

```cpp
class A { protected: int ma; };          // 曾祖父：身份证号
class B : public A { int mb; };          // 爷爷辈
class C : public A { int mc; };          // 另一位爷爷辈
class D : public B, public C { int md; }; // 菱形底边：两条路都通向 A
```

D 从 B 继承到一份 `ma`，又从 C 继承到一份 `ma`——**D 的对象里有两份 A 的数据**，`sizeof(D)` = 20（ma + mb + ma + mc + md）。构造顺序也暴露了重复：**A 构造 → B 构造 → A 构造 → C 构造 → D 构造**，A 的构造函数被执行两次，因为对象里真有两份 A。

这不是语法错误，是**设计错误**。`ma` 若表示姓名，一个人不会有两个名字；表示身份证号，更不可能有两张身份证。两份同义数据摆在那里，访问 `d.ma` 还会直接报二义错误——编译器不知道你说的是 B 路径的 ma 还是 C 路径的 ma，必须写 `d.B::ma` 才能定位。

对多继承本身的工程评价先给出：**能少用就少用**。它一次性复用多个基类的代码，B、C 的指针都能指向 D（多态入口多一条），但菱形这种结构陷阱常常在无意间画出；Java 干脆砍掉了多继承，C++ 标准库里多继承的设计也极少。真要用，必须带着下一节的手术方案。

## 2. 虚继承：把基类数据搬到对象末尾

解法是在继承方式上加 `virtual`：

```cpp
class B : virtual public A { int mb; };
class C : virtual public A { int mc; };
```

`virtual` 修饰成员方法是虚函数；修饰**继承方式**就是**虚继承**，被虚继承的 A 称为**虚基类**。先澄清一个高频混淆：**虚基类与抽象类是两个概念**——抽象类是有纯虚函数的类（第 31 篇），虚基类是被虚继承的类，名字都带"虚"，机制毫无关系。

虚继承对 B 自身的影响，看内存布局（`cl /d1reportSingleClassLayoutB` 可验）：

```text
普通继承的 B（8 字节）          虚继承的 B（12 字节）
┌─────────┐                    ┌─────────┐
│   ma    │ ← A 的数据在这里    │ vbptr   │ ← 原来放 ma 的位置，补一个虚基类指针
├─────────┤                    ├─────────┤
│   mb    │                    │   mb    │
└─────────┘                    ├─────────┤
                               │   ma    │ ← A 的数据被搬到对象末尾
                               └─────────┘
```

虚继承的动作就一句话：**虚基类的数据从原来的位置搬到派生类对象内存的最末尾，原位置补一个 vbptr**。vbptr 指向本类型的 **vbtable**（虚基类表，一个类型一张），表里两行：第一行是 vbptr 距对象起始的偏移（vbptr 在头部时为 0），第二行是 vbptr 到虚基类数据的偏移（B 例中为 8）。

为什么要绕这一道？单看 B 没有意义——ma 搬了个位置还多花 4 字节。它的价值在 D 那里兑现。

## 3. 菱形 + 虚继承：两份变一份

B、C 都虚继承 A 之后，D 的布局变成：

```text
┌──────────────┐
│ B 部分：vbptr、mb   │   ← B 的 vbptr 记着"到 ma 偏移 20"
├──────────────┤
│ C 部分：vbptr、mc   │   ← C 的 vbptr 记着"到 ma 偏移 12"
├──────────────┤
│ md                  │
├──────────────┤
│ ma（虚基类数据）     │   ← 全 D 仅此一份！
└──────────────┘
```

搬移的威力显现：B、C 各自原来那份 ma 都被"搬家规则"推向对象末尾，而末尾只有一个位置——**两份合并成一份**。访问 `d.ma` 不再二义，B 路径和 C 路径的访问经由各自 vbptr 的偏移量，都落到同一格内存。这就是虚继承解决的问题：**派生类只保留一份间接基类的数据**。

三条配套规则随之而来：

**所有直接继承 A 的地方都必须虚继承。**B、C 有一处漏写 virtual，那份漏写的 ma 还会留在中间层——病没除干净。虚继承是"全或无"的手术。

**虚基类的初始化归最终派生类亲自负责。**ma 搬到了 D 的"家门口"，B、C 不再经手它的初始化，D 的构造函数必须在初始化列表里显式调用 A 的构造：

```cpp
D(int data) : B(data), C(data), A(data) { ... }
//                        ^^^^^^ 直接初始化虚基类，绕过 B/C
```

不写会报老朋友般的错误："A 没有合适的默认构造函数可用"——注意这次报错跟第 27 篇的不同：那里是"没指定找默认"，这里是**必须显式**，因为虚基类只有一份，B、C 各自的委托会造成重复初始化，C++ 干脆规定由最派生类一次到位。

**构造顺序里 A 只出现一次**：A 构造 → B 构造 → C 构造 → D 构造，析构相反。

## 4. 附赠的坑：虚继承 + 堆对象 + 基类指针

虚继承还带来一个连带的指针行为，笔试少见但工程里能撞上。第 28 篇说过：**基类指针指向派生类对象时，指向的是"基类部分数据"的起始地址**。普通继承下基类部分在对象开头，指针就指着对象头；虚继承下基类部分被搬到了**末尾**——`A* p = &d;` 里 `p` 指向的是 D 对象**中后部**那个基类部分的起始处，不是 `new` 返回的对象起始地址。

调用虚函数没问题（顺着基类部分的 vfptr 查表，多态照常）。问题出在 `delete p`：释放内存必须从**真实分配的起始地址**开始，而 `p` 指着中后部。这里出现著名的编译器分叉——**MSVC 直接从 `p` 处 free，堆结构损坏，崩溃；GCC（Linux）会在 delete 时自动回偏到真实起始地址，安然无恙**。结论写成守则：虚继承结构里，别用基类指针持有堆上的派生对象；栈对象出作用域自动析构，无此烦恼。

## 小结

- 菱形继承：D 经 B、C 两条路继承 A → 两份 ma（sizeof 多一倍、A 构造两次、访问二义）——设计错误而非语法错误
- 多继承评价：复用更多代码、多态入口更多，但菱形陷阱常在无意间画出；能避则避，Java 已砍掉
- 虚继承（`virtual` 修饰继承方式）→ 被继承者成虚基类（与抽象类完全是两回事）；基类数据搬到派生类对象末尾，原位补 vbptr → vbtable（两行偏移量）
- 菱形全链虚继承后 ma 只剩一份；**所有**直接继承处都必须 virtual；虚基类由最终派生类在初始化列表里**显式初始化**（`: B(data), C(data), A(data)`）
- vbptr/vbtable 与 vfptr/vftable 并列：前者管虚基类数据定位，后者管虚函数查表；两者共存不影响多态
- 虚继承下基类指针指向对象中后部（基类部分起始处）；MSVC 对这种指针做 delete 会崩，GCC 自动回偏——虚继承结构避免用基类指针管堆对象
