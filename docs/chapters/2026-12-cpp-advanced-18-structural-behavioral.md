# 代理、装饰器、适配器与观察者：组合的艺术与通信的解耦

![代理（控制访问）/装饰器（增强功能）/适配器（接口转换）三兄弟 + 观察者（发布订阅）](/assets/images/cpp-advanced/cpp-advanced-18-structural-behavioral.png)

设计模式按关注点分三大族：**创建型**管对象怎么产生（单例、工厂，前两篇）；**结构型**管类与类怎么组合出功能（代理、装饰器、适配器）；**行为型**管对象之间怎么通信（观察者）。本篇把后两族的高频成员一次讲完——校招里代理、适配器、观察者都是常客。

四个模式的共同底座依旧是多态：**抽象基类 + 组合/继承 + 基类指针**（第 30 篇）。区别只在"组合的方式"与"通信的方向"。

边界：模式只讲结构与意图，每种一个最小案例；代理的远程/写时拷贝等变体不展开。

## 1. 代理与装饰器：同一副骨架，两种意图

代理与装饰器的结构**几乎一模一样**：抽象基类派生出"真实类"与"包装类"，包装类内部**持有一个真实类的对象**（组合），把调用转发给它——委托。

```cpp
class Subject                       // 抽象接口
{
public:
    virtual void doWork() = 0;
    virtual ~Subject() {}
};

class RealSubject : public Subject  // 真实类：完整功能
{
public:
    void doWork() { /* 核心逻辑 */ }
};

class Proxy : public Subject        // 包装类：持有 RealSubject
{
    RealSubject real_;
public:
    void doWork() { /* 前置处理 */ real_.doWork(); /* 后置处理 */ }
};
```

客户端只能通过包装类访问（真实类的构造同样收进 private 或包内），"委托 + 前后处理"的骨架完全一致——**区别全在意图**：

- **代理模式**：前后处理做的是**控制**——权限检查（没登录不让调）、延迟加载（用时才构造真实对象）、日志审计。核心功能一个不变，控制访问是目的；
- **装饰器模式**：前后处理做的是**增强**——给功能附加新能力（日志装饰器给文件操作加记录、缓存装饰器给查询加快取）。装饰器可以层层叠加（装饰器套装饰器），功能越包越多是目的。

一句话分清：**代理管"能不能调"，装饰器管"调了之后多点什么"**。两者都是"不改真实类"的前提下改变它的对外行为——开闭原则的结构型落地。

## 2. 适配器：接口不对齐时的转换层

适配器的场景在公司开发里天天发生：**引入第三方库，它的接口跟我们系统的接口不兼容**——不能改第三方源码，也不想改我们系统的调用方，中间加一层转换：

```cpp
class Target                    // 我们系统期望的接口
{
public:
    virtual void request(int type, const string& data) = 0;
    virtual ~Target() {}
};

class Adaptee                   // 第三方库：接口形状不同
{
public:
    void specificRequest(const string& json) { /* 第三方实现 */ }
};

class Adapter : public Target   // 适配器：继承目标接口 + 组合被适配者
{
    Adaptee adaptee_;
public:
    void request(int type, const string& data)
    {
        string json = pack(type, data);   // 形状转换
        adaptee_.specificRequest(json);
    }
};
```

结构上与代理同族（继承接口 + 组合实现），意图则不同：**适配器管"接口转换"**——让两个形状不匹配的类合作。与代理/装饰器的分界：代理与装饰器的包装类和真实类**接口相同**（同族增强/控制）；适配器的包装类与被适配者**接口不同**（跨族转换）。

## 3. 观察者：一对多通知，发布订阅

行为型模式关注**对象之间的通信**。最笨的通信是 A 直接调 B 的方法——A 死死依赖 B；依赖一多，改一处动全身。观察者模式（也叫监听者、发布订阅模式）把通信解耦：

```cpp
class Observer                  // 抽象观察者
{
public:
    virtual void update(int msg) = 0;
    virtual ~Observer() {}
};

class Subject                   // 被观察者：只认识抽象观察者
{
    list<Observer*> observers;
public:
    void addObserver(Observer* o)   { observers.push_back(o); }
    void removeObserver(Observer* o) { observers.remove(o); }
    void notify(int msg)             { for (auto o : observers) o->update(msg); }
};
```

被观察者（发布方）维护一张观察者名单，状态变化时遍历通知；观察者（订阅方）各自实现 update 响应。**被观察者不认识任何具体观察者**——新增一种订阅者只需实现 Observer 并注册，发布方零改动（又是开闭原则）。一个状态变化、多方响应的"一对多"场景（GUI 事件、行情推送、消息总线）全是它的领地。

muduo 网络库的回调用 function 注册（第 12 篇），本质是观察者思想的现代形态——**用"函数对象名单"替代"继承 Observer 的对象名单"**，结构更轻，解耦的意图一脉相承。

## 4. 四模式一张表

| 模式 | 族 | 结构 | 意图 |
|---|---|---|---|
| 代理 | 结构型 | 委托 + 前后处理 | 控制访问（能不能调） |
| 装饰器 | 结构型 | 委托 + 前后处理（可叠加） | 增强功能（多点什么） |
| 适配器 | 结构型 | 继承目标接口 + 组合被适配者 | 接口转换（形状对齐） |
| 观察者 | 行为型 | 名单 + 遍历通知 | 一对多通信解耦 |

四个模式零新语法——全是第 30 篇多态的排列组合。设计模式的学习终点不是背 23 个名字，而是拿到场景能对号：**要控制 → 代理；要增强 → 装饰器；接口不合 → 适配器；一对多通知 → 观察者；要唯一 → 单例；要解耦构造 → 工厂**。

## 小结

- 三大族：创建型管产生、结构型管组合、行为型管通信——底座全是多态
- 代理与装饰器同骨架（委托 + 前后处理），意图分界：控制访问 vs 功能增强；装饰器可叠加
- 适配器与代理同族不同意图：包装类与被适配者接口不同（跨族转换），处理第三方库接口不兼容
- 观察者：被观察者只认识抽象观察者，新增订阅者零改动发布方——一对多通信的开闭落地；muduo 的 function 回调是它的现代形态
- 对号入座：控制→代理、增强→装饰器、接口不合→适配器、一对多→观察者、唯一→单例、解耦构造→工厂
