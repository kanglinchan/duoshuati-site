# 函数重载：编译器眼里根本没有"重载"这两个字

![C 与 C++ 的符号生成规则差异：C 只有函数名，C++ 是函数名加参数列表类型](/assets/images/cpp-core/cpp-core-09-overloading.png)

三个函数，名字都叫 `compare`，一个比两个 `int`，一个比两个 `double`，一个比两个字符串。把它们放进 `.cpp` 文件，编译、运行，一切正常；放进 `.c` 文件，链接器当场翻脸：多个符号重定义。

同一个名字凭什么在 C++ 里能共存？这个问题背后藏着 C 和 C++ 最关键的一个差异——**编译器怎么给函数起"符号名"**。看穿这一层，函数重载的三道面试题（为什么 C++ 支持 C 不支持、要注意什么、C 和 C++ 怎么互相调用）全是同一件事的三种问法。

边界：本文只讲普通函数的重载；类成员方法之间"重载、隐藏、覆盖"的纠缠在继承篇单独处理；重载决议的精确匹配规则（精确匹配 > 提升 > 转换 > ...）属于更深的编译器话题，这里不铺开。

## 1. 同名的函数为什么能共存

例. 三胞胎登场：

```cpp
bool compare(int a, int b)                  { return a > b; }
bool compare(double a, double b)            { return a > b; }
bool compare(const char* a, const char* b)  { return strcmp(a, b) > 0; }

compare(10, 20);            // 匹配第一个
compare(10.0, 20.0);        // 匹配第二个
compare("abc", "abd");      // 匹配第三个
```

解. 编译器根据**调用处实参的类型**挑选对应版本：传两个 `int` 选第一个，传两个 `double` 选第二个，传两个字符串选第三个。一组函数，函数名相同、参数列表的个数或类型不同——这就是**函数重载**（overload）。

但"编译器很聪明，会挑"是个假象。它不是在运行时挑，也不存在一个"重载表"供它查询。真相在符号表里，下一节拆开。

## 2. 符号生成规则：一切的关键

第 02、03 篇讲过：`.o` 文件之间靠**符号**互通，函数的定义是一个符号的定义，调用是一个对符号的引用，链接器做符号解析。所以"同名的两个函数能不能共存"等价于"同名的两个函数会不会生成两个相同的符号"。

**C 编译器：符号只由函数名决定。**三个 `compare` 生成的符号全是 `_compare`。链接器看到三个同名符号的定义——重定义，链接错误。所以 C 语言里同名函数连编译期都过不去，更谈不上调用。

**C++ 编译器：符号由函数名 + 参数列表类型共同决定。**三个 `compare` 的符号各不相同（可以想象成 `_compare_int_int`、`_compare_double_double`、`_compare_pcp` 这样的形式；MSVC 里的真实名字形如 `?compare@@YAHHH@Z`，GCC 下可用 `c++filt` 命令还原阅读）。

同名函数在 C++ 里生成的是**三个不同的符号**，链接器眼里它们本来就是三个函数——"重载"这个概念只活在语法层，编译器和链接器从头到尾只认符号。这就是本文标题的含义：编译器眼里根本没有重载。

这个规则同时解释了一条否定性结论：**返回值不参与符号生成**，符号里没有返回值的份。所以两个函数仅仅返回值不同，生成的符号一模一样，不构成重载，编译器直接报重定义。

## 3. 重载的完整条件清单

一组函数要构成重载，要同时满足三条：

**条件一：函数名相同，参数列表的个数或类型不同。**这是定义的一半。

**条件二：必须在同一作用域。**这条最容易被忽视，坑也最深。看这段：

```cpp
bool compare(int a, int b) { return a > b; }
bool compare(double a, double b) { return a > b; }

void demo()
{
    bool compare(int, int);      // 函数内的局部声明，合法

    compare(10.0, 20.0);         // 警告：double 转 int 可能丢精度
    compare("abc", "abd");       // 错误：const char* 无法转 int
}
```

两个 `double` 实参居然试图匹配 `int` 版本。原因：函数里声明过一个叫 `compare` 的函数之后，调用点在**最近的局部作用域**找到了这个名字，查找就此停止——它不会再跑到全局作用域去找有没有更合适的版本。于是两个调用都被塞给局声明的 `compare(int, int)`，一个警告一个错误。

变量作用域的规则原样适用于函数名：局部同名声明**遮蔽**了全局的一组重载，不是"加入"它们。所以重载这组函数必须**从调用点看处在同一个作用域**——这条结论会原样出现在继承篇的"隐藏"里。

**条件三：形参类型要真的不同。**顶层 `const` 不改变类型：

```cpp
void f1c(int a);
void f1c(const int a);       // 错误：已有主体
```

第 05 篇讲过：`const` 右边没有指针时不参与类型。`int` 和 `const int` 在编译器眼里是同一个类型，两个函数生成同一个符号，是重定义不是重载。（`const int*` 和 `int*` 则是两种类型，可以重载——区别就在 `const` 右边有没有 `*`。）

## 4. 重载是静态多态

"什么是多态"的面试标准答案是：多态分**静态多态**（编译期）和**动态多态**（运行期），静态多态包括函数重载和模板，动态多态是虚函数机制。

函数重载为什么算多态？一个名字 `compare`，随实参不同呈现多种形态——这确实是"多种形态"。而它静态在哪？**调用点到底执行哪个版本的指令，在编译期生成指令时就已确定**：实参要入栈、要 `call` 一个确定的地址，没有任何一条决策留到运行时。模板同样在编译期实例化，所以两者同属静态多态。虚函数那一半，到继承篇再会合。

## 5. extern "C"：两种符号规则之间的桥

符号规则不同带来一个工程问题：C 和 C++ 的二进制产物怎么互相调用？

**C++ 调用 C。**写一个 `sum.c`，在 C++ 里声明 `int sum(int, int);` 再调用，链接报"无法解析的外部符号"。原因用第 2 节就能推出来：C++ 编译器按自己的规则给这个**引用**生成符号（带了参数列表），而 `sum.c` 里躺着的**定义**符号是 C 规则的裸 `sum`——名字对不上，解析失败。

修法是把 C 函数的声明包进 `extern "C"`：

```cpp
extern "C" int sum(int a, int b);
```

这是给 C++ 编译器的指令："这个名字按 C 规则生成符号，别往里掺参数列表。"引用符号变成了裸 `sum`，与定义一拍即合。

**C 调用 C++。**方向反过来，主动权在 C++ 源那边：把提供给 C 使用的函数定义（或声明）用 `extern "C"` 包起来，让符号按 C 规则生成，C 项目就能直接链接调用。注意 `extern "C"` 是 C++ 语法，**C 编译器不认识它**，绝不能把 `extern "C"` 写进会被 C 编译器编译的代码里。

**两全其美的头文件范式。**一个头文件既会被 C 项目包含、又会被 C++ 项目包含时，用编译器内置宏 `__cplusplus` 做条件编译：

```cpp
#ifdef __cplusplus
extern "C" {
#endif

int sum(int a, int b);
int sub(int a, int b);

#ifdef __cplusplus
}
#endif
```

`__cplusplus` 只有 C++ 编译器才定义。C++ 编译这份头文件时，声明带上 `extern "C"`；C 编译器预处理时这段根本不存在，声明原样生效——两个编译器拿到的是同一份文本，产出的符号都符合 C 规则。这是所有跨语言 C 接口头文件的标准写法，读第三方库头文件时你会反复见到它。

## 小结

- C 符号 = 函数名；C++ 符号 = 函数名 + 参数列表类型。"重载"只存在于语法层，编译器与链接器只认符号
- C++ 支持重载、C 不支持，唯一原因就是符号生成规则不同
- 重载三条件：名字相同参数不同、**同一作用域**（局部声明会遮蔽全局整组重载）、形参类型真的不同（顶层 const 不算，返回值不算）
- 函数重载是静态多态：调用版本在编译期生成指令时确定
- C++ 调 C：声明包 `extern "C"`；C 调 C++：把定义包 `extern "C"`；头文件通用范式：`#ifdef __cplusplus` 包 `extern "C" {}`
